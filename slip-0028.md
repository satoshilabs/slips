# SLIP-0028 : Transaction verification statements

```
Number:  SLIP-0028
Title:   Transaction verification statements
Type:    Standard
Status:  Draft
Authors: Petr Susil <petr.susil@satoshilabs.com>
Created: 2026-09-29
```

## Abstract

A transaction statement is a human-readable account of the security-relevant effects of the outputs of a transaction, such as the assets the payer sends or which are delivered to an address, which a wallet displays before it authorizes the transaction, together with attributes of the parties and assets involved, such as the name of an address.
An attestation is a commitment to a statement, established by evidence which the wallet verifies under a trust anchor it holds.
The attestation is issued by a party or mechanism which the wallet trusts for that purpose, and which need not be the party that requested the payment.

## Motivation

A wallet can authenticate the destination and the amount of an output, but that does not establish what the output does.
Bitcoin `OP_RETURN` data and EVM calldata are transaction data which an address and an amount do not describe, and whose meaning depends on a protocol the wallet may not implement.
A wallet which cannot establish the effects of such an output can only present it as opaque data (*blind signing*) or refuse to sign it.

This specification defines a statement, which describes those effects in a form the wallet can display, and an attestation, which allows the verification of the statement to be performed elsewhere and checked by the wallet.
A statement in a payment request is trusted as far as the payment request signer is; an attestation establishes it independently.

A statement and its attestation are defined independently of any payment request, so that they can also be used when a transaction is signed without one.

## Statement

```
statement = summary || n || entry_1 || ... || entry_n
entry     = entryType || coinType || body
```

* *summary* (length-prefixed UTF-8 string): a short description of the action by the party which makes the statement.
* *n* (CompactSize integer, minimally encoded): the number of entries, which MUST be distinct and in ascending lexicographic order of their encodings.
* *entryType* (1 byte): an *effect* below 0x80 or an *attribute* from 0x80, see below.
* *coinType* (4 bytes): the SLIP-0044 coin type of the asset or of *party*, little-endian.
* *body*: the fields of *entryType*.

The fields are:

* *asset* (length-prefixed): an asset under *coinType*, empty for the native asset. For EVM coin types, the 20-byte contract address, followed for a non-fungible or multi-token contract by the 32-byte big-endian token identifier.
* *bound* (1 byte): 0x00 exact, 0x01 at least, 0x02 at most, 0x03 unbounded.
* *amount*: in the smallest unit of the asset, encoded as the amount of a requested output in [SLIP-0024](slip-0024.md); zero if unbounded.
* *party* (length-prefixed): an address, encoded as the address of a requested output in [SLIP-0024](slip-0024.md).
* *name*, *label* (length-prefixed UTF-8 strings): a name or a label of *party*.
* *accountType* (1 byte): 0x00 controlled by a key, 0x01 a contract, 0x02 controlled by a key and delegated to code, such as by EIP-7702.
* *received* (1 byte): 0x00 if *party* has not received an asset from the payer before, 0x01 if it has.

Length prefixes are minimally encoded CompactSize integers.

| *entryType* | *body* | Entry | Permitted *bound* |
| ----------- | ------ | ----- | ----------------- |
| 0x01 | *asset* \|\| *bound* \|\| *amount* \|\| *party* | *send*: the payer transfers the asset to *party*. | exact, at most, unbounded |
| 0x02 | *asset* \|\| *bound* \|\| *amount* \|\| *party* | *deliver*: the asset is delivered to *party*. | exact, at least |
| 0x03 | *asset* \|\| *bound* \|\| *amount* \|\| *party* | *approve*: *party* may transfer the asset from the payer. | exact, unbounded |
| 0x04 | *asset* \|\| *bound* \|\| *amount* \|\| *party* | *delegate*: *party* obtains authority over the asset, or over every asset of the payer under *coinType* if *asset* is empty. | unbounded |
| 0x81 | *party* \|\| *name* | *address name*: *name*, such as an ENS name, resolves to *party*. | |
| 0x82 | *party* \|\| *label* | *label*: *party* is labelled *label* in a registry which the method defines. | |
| 0x83 | *party* \|\| *accountType* | *account type*: *party* is of type *accountType*. | |
| 0x84 | *party* \|\| *received* | *history*: whether *party* has received an asset from the payer before. | |
| 0x85 | *asset* \|\| *bound* \|\| *amount* \|\| *party* | *existing allowance*: before the payload is executed, *party* may transfer up to *amount* of the asset from the payer; a change of it is an approve. | exact |

Effects describe the successful execution of the payload; fees are outside the statement.
The bound limits the payer's loss, or for a deliver the amount delivered. An approve or a delegate is stated as if it does not lapse.
A method MUST NOT apply to a payload with a security-relevant effect which these types cannot express.
The effects of a statement account for every security-relevant effect of the payload.
An attribute asserts a fact which holds when the statement is made.
The entries of a statement MUST NOT contradict each other.

## Displaying a statement

A wallet which relies on a statement MUST display its summary as a description by the party which makes the statement, separately from the effects and not as verified.
It MUST display one line for each effect and, in a state assertion, for each attribute, in the order of the encoding, worded from the entry alone as follows or as a localized equivalent:

| Entry | Rendering |
| ----- | --------- |
| send, exact | Send *amount* to *party* |
| send, at most | Send at most *amount* to *party* |
| send, unbounded | Send any amount of *asset* to *party* |
| deliver, exact | Deliver *amount* to *party* |
| deliver, at least | Deliver at least *amount* to *party* |
| approve, exact | Allow *party* to spend up to *amount* |
| approve, unbounded | Allow *party* to spend any amount of *asset* |
| delegate | Give *party* control of *asset*, or of the account if *asset* is empty |
| address name | *name* is *party* |
| label | *party* is labelled *label* |
| account type | *party* is controlled by a key, is a contract, or is delegated to code |
| history | *party* has not received from you before, or has received from you before |
| existing allowance | *party* may already spend up to *amount* |

The wallet formats *amount* and *asset* using metadata it trusts for *coinType* and *asset*, such as signed definitions; without it, the wallet MUST display the asset identifier and the amount in the smallest unit, or refuse the statement.
An unbounded effect MUST be displayed distinguishably from a bounded one.
The wallet MAY display the rendering of an attribute next to each displayed address which matches its *coinType* and *party*, and MUST NOT display it in place of the address.

The wallet MUST reject a statement which is malformed or non-canonical, has trailing data, violates a constraint of [Statement](#statement), or contradicts facts which the wallet establishes itself, including the metadata it trusts.

## Attestation

An attestation is the concatenation of the following fields:

* *statement* (variable length): the attested statement, encoded as defined in [Statement](#statement).
* *verificationMethod* (4 bytes): 32-bit identifier of the verification method in little-endian byte order, see [Verification methods](#verification-methods).
* *attester* (length-prefixed binary string): identifier of the trust anchor under which the evidence for *attestationHash* is verified.
* *verificationData* (length-prefixed binary string): method-specific parameters and evidence.

## Payload

The *payload* is the requested outputs of the payment request where the attestation is used with one, and otherwise every output of the transaction being signed, in order. It is empty for a *state assertion*, an attestation which applies to no output, as determined by *verificationMethod*. The statement of a state assertion MUST have no effects.
The wallet MAY use the attributes of a state assertion which it has accepted when it displays the transaction for which it issued the nonce, as if they were attributes of its statement, and MUST reject the transaction if these attributes and those of its statement contradict each other.
The wallet computes

```
payloadHash = SHA256(output_1 || output_2 || ... || output_n)
```

from the transaction being signed, where *output*<sub>*i*</sub> is encoded as defined in [SLIP-0024](slip-0024.md), *Signature generation*.

## Verification context

The *verification context* encodes the facts outside the payload which can affect the statement:

```
verificationContext = coinType || nonce || methodContext
```

where *coinType* is the 32-bit little-endian SLIP-0044 coin type, which identifies the chain as defined in [SLIP-0024](slip-0024.md), *Coin type of EVM chains*;
*nonce* is a length-prefixed unpredictable challenge issued by the wallet;
and *methodContext* is defined by the verification method.

The wallet MUST derive the verification context from the transaction and the payment request, not from *verificationData*.
It MUST refuse a chain which has no registered coin type of its own and an attestation whose nonce it did not issue for the transaction being signed, and MUST invalidate the nonce when it signs or refuses that transaction.

## Attestation hash

```
attestationHash = SHA256(b"\x53\x4c\x28\x41" || verificationMethod || attester || payloadHash || SHA256(verificationContext) || statement)
```

where the fields are encoded as in the attestation.
The wallet computes *attestationHash* itself; it is not part of the attestation.

## Evidence

*attestationHash* MUST be established by evidence in *verificationData* which the wallet verifies under a trust anchor it holds for the method. The wallet MUST NOT rely on an attestation unless the evidence establishes the value of *attestationHash* which it computed.

## Verification methods

A verification method determines both how the statement is derived and how the attestation is established; the same derivation established in different ways constitutes different methods.
Each *verificationMethod* identifies exactly one method, which applies either to payloads or to state assertions. The wallet MUST reject an attestation for a method it does not implement.

A method MUST produce a *complete* statement, whose effects account for every *security-relevant effect* of the payload — any loss of the payer's assets, or any claim on them or on authority over them, now or later.
Each attribute of the statement MUST be established by the method, and MUST hold in a state observed after the nonce is issued.

A statement depends on the payload alone (*interpretation*), on the payload executed against an observed state (*simulation*), or on an observation of mutable state (*dynamic state*);
where a statement mixes these, the strongest dependence applies. For a statement to be complete, an interpretation MUST bound each effect under the semantics the method covers
or mark it unbounded; a simulation MUST bound each effect by a condition which transaction validity or execution enforces or mark it unbounded; a dynamic state MUST be observed after the nonce is issued.

A method MUST define:

* the payloads or state assertions to which it applies;
* the evidence in *verificationData* and the trust anchor which *attester* identifies;
* its *methodContext*, which MUST determine every other fact known to the wallet which can affect the statement;
* how it establishes the effects and the attributes of the statement.

## Use with a payment request

A wallet MAY require an attestation for a statement memo of a [SLIP-0024](slip-0024.md) payment request.
The nonce and *coinType* of the attestation are those of the payment request, its *statement* MUST be identical to the statement of the memo,
the attestation MUST NOT be a state assertion, and the wallet MUST reject the payment request otherwise.
