Type:    Standard
Status:  Draft

## Abstract

A transaction statement is a human-readable account of the security-relevant effects of a transaction, such as the assets which the payer sends or which are delivered to an address. It also contains attributes of the parties and assets involved, such as the name of an address. A wallet displays the statement, or checks it against a policy, before it authorizes the transaction.
An attestation establishes a statement by evidence which the wallet verifies under a trust anchor it holds.
It is issued by a party or mechanism which the wallet trusts for that purpose. This need not be the party that requested the payment.

## Motivation

A wallet can authenticate the destination and the amount of an output, but that does not establish what the output does.
Bitcoin `OP_RETURN` data and EVM calldata are transaction data which an address and an amount do not describe, and whose meaning depends on a protocol the wallet may not implement.
A wallet which cannot establish the effects of such an output can only present it as opaque data (*blind signing*) or refuse to sign it.

This specification defines a statement, which describes those effects in a form the wallet can display or check against a policy.
It also defines an attestation, which lets the statement be verified elsewhere and checked by the wallet.
A statement in a payment request is trusted as far as the payment request signer is. An attestation establishes it independently.

A statement and its attestation are defined independently of any payment request, so that they can also be used when a transaction is signed without one.
With [signing hash binding](#signing-hash-binding), they are also independent of the chain. The issuer of the attestation interprets the transaction, and the wallet needs only the hashes which it signs.

## Encoding

The structures which this specification defines are [CBOR](https://www.rfc-editor.org/rfc/rfc8949) data items, described in [CDDL](https://www.rfc-editor.org/rfc/rfc8610).
They are encoded in deterministic encoding, as defined in RFC 8949, Section 4.2.1 (*Core Deterministic Encoding Requirements*), so that every data item has exactly one encoding. An unsigned integer below 2<sup>64</sup> MUST be encoded as major type 0 (uint). An unsigned integer from 2<sup>64</sup> to 2<sup>256</sup> - 1 MUST be encoded as a positive bignum (tag 2, #6.2) over a byte string of 9 to 32 bytes whose first byte is non-zero. *SHA256*(*x*) of a data item *x* is the SHA-256 hash of its deterministic encoding.
The wallet MUST reject non-deterministic encoding. For an unsigned field it MUST also reject values outside the range of *uint256*, tag 2 encodings of values below 2<sup>64</sup>, and leading zero bytes.

## Statement

A statement consists of entries, each of which is an effect or an attribute:

* An *effect* is a net change which the transaction makes, or causes a protocol to make afterwards, such as a transfer of an asset or an authority granted over it, affecting either the payer or another account (subject) on whose behalf the transaction acts. An *effect* holds if the execution of the transaction succeeds. A fee, and any other *effect* which persists when the execution fails, such as the delegation of an EIP-7702 authorization, holds in either case.
* An *attribute* is a fact about a party or an asset which holds when the statement is made, such as the name of an address.

### Format

```
statement = [* entry]
entry     = effect / attribute

effect    = [effectType, chain, asset, bound, amount, party, ? subject]
attribute = addressNameEntry / labelEntry / codeStateEntry
          / historyEntry / existingAllowanceEntry / codeHashEntry

addressNameEntry       = [129, chain, party, name]                  ; 0x81
labelEntry             = [130, chain, party, label]                 ; 0x82
codeStateEntry         = [131, chain, party, codeState]             ; 0x83
historyEntry           = [132, chain, asset, party, received]              ; 0x84
existingAllowanceEntry = [133, chain, asset, bound, amount, party, ? subject] ; 0x85
codeHashEntry          = [134, chain, party, codeHash]              ; 0x86

effectType = 1..8                                        ; 0x01 to 0x08
asset      = tstr / null
bound      = 0..3
uint256    = uint / #6.2(bstr .size (9..32))
amount     = uint256
party      = bstr
subject    = bstr
safeText   = tstr .size (1..64)
name       = safeText
label      = safeText
codeState  = 0..2
received   = bool
codeHash   = bstr .size 32
```

The entries MUST be distinct and in ascending lexicographic order of their deterministic CBOR encodings. Note that CBOR array headers sort shorter arrays (4-element attributes, initial byte 0x84) before longer arrays (6- or 7-element entries, initial byte 0x86 or 0x87). The first element of an entry is its *entryType*, below 0x80 for an effect and from 0x80 for an attribute, as listed below. *chain* is the *chain* of the *asset* or of *party*, see [Chains](#chains). The other elements are:

* *asset*: an *asset* on *chain*, encoded as defined in [Accounts and assets](#accounts-and-assets), or, ONLY in a delegate (0x04), null for every *asset* of the payer (or subject) on *chain*.
* *bound*: 0 exact, 1 at least, 2 at most, 3 unbounded.
* *amount*: an unsigned integer below 2<sup>256</sup> in the smallest unit of the asset, or 0 if bound is unbounded (3). When *bound* is 3, *amount* MUST be 0.
* *party*: an account on *chain*, encoded as defined in [Accounts and assets](#accounts-and-assets), or empty (h'') ONLY in a fee (0x06). In every entry other than 0x06, *party* MUST be non-empty.
* subject: the account on *chain* whose assets or authority are affected when that account is not the payer (such as a multisig, vault, or smart account invoked by the payer). A present *subject* MUST be a non-empty account encoded as defined in [Accounts and assets](#accounts-and-assets). It MUST be omitted when equal to the payer on *chain*, and MUST be omitted in deliver (0x02) and deferred deliver (0x05).
* *name*, *label*: a UTF-8 string in Unicode Normalization Form C (NFC) of 1 to 64 bytes naming or labelling *party*. The wallet MUST reject any character in Unicode general categories Cc (control), Cf (format), Zl (line separator) or Zp (paragraph separator). For ENS names, *name* MUST be normalized according to ENSIP-15.
* *codeState*: 0 if *party* is controlled only by keys, 1 if it is controlled by code, such as a contract or a program, 2 if it is controlled by keys and delegates to code, such as by EIP-7702.
* *received*: true if any finalized transaction on *chain* included before the statement is made transferred a non-zero amount of the specified *asset* from the payer to *party* with the payer’s authorization for that transfer, false otherwise. Unauthenticated third-party transfers (such as zero-value ERC-20 transferFrom calls) MUST NOT set *received* to true.
* *codeHash*: the hash of the code of *party*, as the *chain* defines it. On EVM chains, this is keccak256 of the account's code (0xc5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470 for a non-empty account with no code), or 32 zero bytes for a nonexistent or EIP-161 empty account, as specified by EIP-1052.

| *entryType* | Elements after *chain* | Entry | Permitted *bound* |
| :--- | :--- | :--- | :--- |
| 0x01 | *asset*, *bound*, *amount*, *party*, ? subject | *send*: the payer (or subject) transfers the *asset* to *party*. | exact, at most, unbounded |
| 0x02 | *asset*, *bound*, *amount*, *party* | *deliver*: the *asset* is delivered to *party*. | exact, at least |
| 0x03 | *asset*, *bound*, *amount*, *party*, ? subject | *approve*: *party* may transfer the *asset* from the payer (or subject). | exact, at most, unbounded |
| 0x04 | *asset*, *bound*, *amount*, *party*, ? subject | *delegate*: *party* obtains authority over the *asset*, or over every *asset* of the payer (or subject) on *chain* if *asset* is null. | unbounded |
| 0x05 | *asset*, *bound*, *amount*, *party* | *deferred deliver*: a protocol delivers the *asset* to *party* after the execution of the transaction, if it completes the delivery. | exact, at least |
| 0x06 | *asset*, *bound*, *amount*, *party*, ? subject | *fee*: the payer (or subject) pays a *fee* in the *asset* for the transaction. *party* MUST be empty. A *fee* is stated only with signing hash binding. | exact, at most, unbounded |
| 0x07 | *asset*, *bound*, *amount*, *party*, ? subject | *stake*: the *asset* of the payer (or subject) is bonded to *party*, such as a validator, which can cause its loss by slashing. | exact, at most, unbounded |
| 0x08 | *asset*, *bound*, *amount*, *party*, ? subject | *debt*: *party* obtains a claim of the *asset* on the payer (or subject), which it can enforce against its assets, such as by the liquidation of collateral. | exact, at least, unbounded |
| 0x81 | *party*, *name* | *address name*: *name*, such as an ENS *name*, is the primary reverse-and-forward verified *name* of *party*. | - |
| 0x82 | *party*, *label* | *label*: *party* is labelled *label* in a registry which the method defines. | - |
| 0x83 | *party*, *codeState* | *code state*: *party* is controlled as *codeState* states. | - |
| 0x84 | *asset*, *party*, *received* | *history*: whether *party* has previously *received* a non-zero payer-authorized *asset* transfer on *chain*. | - |
| 0x85 | *asset*, *bound*, *amount*, *party*, ? subject | *existing allowance*: before the transaction is executed, *party* may transfer up to *amount* of the *asset* from the payer (or subject). | exact |
| 0x86 | *party*, *codeHash* | *code hash*: the code of *party* has the hash *codeHash*. | - |

### Effects

The effects of a statement account for every [security-relevant effect](#completeness) of the transaction, or of its payload with [payload binding](#payload-binding). A method MUST NOT apply to a transaction, or with payload binding to a payload, with a security-relevant effect which the entries above cannot express.
The key of an effect is (effectType, chain, asset, party, subject), taking omitted subject as empty. A statement MUST NOT contain two effects with equal keys; multiple transfers or allowance changes sharing a key MUST be aggregated into a single net post-transaction effect.
For a send, *party* is the first recipient of the asset from the payer or subject. For example, ETH sent as call value goes to the router even if the router forwards it to a pool. A method MUST deduct a same-execution refund of that payment in the same asset to the original funding account before stating the send. Use an exact amount when fixed, otherwise the maximum net debit enforced by the operation. Omit a fully refunded send. An independent delivery or a deferred return is a separate effect. If the method cannot establish the counterparty, it MUST decline to attest. If the maximum is unbounded it MUST state an unbounded send. Where the operation permits a net credit beyond a full refund, the method MUST account separately for the additional delivery.
The bound of an effect limits the loss of the payer (or subject). For a deliver or a deferred deliver, it limits the amount delivered. For a debt, it states the amount owed, which can grow. An approve states the resulting post-transaction allowance as if it does not lapse; an explicit revocation (exact, amount 0) MAY be stated when paired with a non-zero existingAllowanceEntry for the same chain, asset, party and subject, and MUST otherwise be omitted. A delegate is stated as if it does not lapse. For an EIP-7702 revocation the method MUST set *party* to the 20-byte zero address and the wallet MUST display “Revoke account delegation”.

Each effect is worded as follows:

| Effect | Wording when *subject* is omitted |
| :--- | :--- |
| send | Send {*e*} to {*party*} |
| deliver | Deliver {*e*} to {*party*} |
| approve | Allow {*party*} to spend {*e*} (or "Revoke {*party*}'s allowance of {*asset*}" if exact 0) |
| delegate | Delegate {*asset*, or the account if *asset* is null} to {*party*} |
| deferred deliver | Deliver {*e*} to {*party*}, later |
| fee | Pay a fee of {*e*} |
| stake | Stake {*e*} with {*party*} |
| debt | Owe {*e*} to {*party*} |

{*e*} stands for the bound, the amount and the *asset* of the effect, such as "at least 2450 USDC", or "any amount of USDC" if it is unbounded, or "all {collection}" for a collection-wide NFT/multi-token approval.
The amount and the asset are formatted with metadata which the wallet trusts, or otherwise shown as the asset identifier and the amount in the smallest unit.
For a present *subject*, prefix the wording with “Account {*subject*}: ”. The wallet MUST identify this account when it evaluates an account-specific policy.
Where the chain of an effect is not the chain of the transaction being signed, the wallet adds "on {*chain*}" after {*party*}, or after {*e*} for a fee.

A deferred deliver is made by a protocol after the execution of the transaction, such as by a bridge which delivers an asset on another chain, or by a contract which releases an asset after a delay. Every other effect is made by the execution of the transaction.
A method states a deferred deliver only under the semantics of the protocol which it covers. The bound of a deferred deliver is the condition which that protocol enforces, and the deliver holds only if the protocol completes it.
A method MUST NOT apply if the protocol permits an outcome which the effects cannot express, such as a release of the asset to a party other than the payer.
Trust in such a method includes trust in the verifier of the protocol and in the consensus of the chains where it verifies proofs, or otherwise in its operators.

A fee is any amount which the payer (or subject) pays for the inclusion or the execution of the transaction. With payload binding, the fee is outside the statement. Where the payer signs only some inputs of a UTXO transaction, such as in a coinjoin or multi-party PSBT, its fee is max(0, min(txTotalFee, payerInputs - payerSelfOutputs - payerSends)), in the native asset, where txTotalFee is total inputs less total outputs, payerInputs is the sum of inputs controlled by the payer, payerSelfOutputs is the sum of outputs delivered to the payer, and payerSends is the exact native value funded by the payer for payments to other parties, excluding change and fees. The method MUST establish this attribution before using the formula. If it cannot, it MUST decline to attest. Omit a zero fee. Rollups which meter L1 data costs inside the transaction gas limit (such as Arbitrum) enforce an upper bound on the total fee (`at most`). Where a part of the fee is billed outside the transaction gas limit without an execution-enforced ceiling, such as the L1 data fee of an OP Stack rollup, the fee is stated as unbounded unless bounded under the method's documented state assumptions; a method that supports a separate policy limit for L2 execution MUST bind its execution fee cap in *methodContext*. A wallet relying on such a limit MUST derive the cap from the transaction it signs or reject the attestation. The cap alone does not bound the total fee.
Other changes are stated with the entries above. A lock of liquid funds is a send and a deferred deliver to the payer; an unbonding of already-staked funds without transferring additional liquid funds is a deferred deliver to the payer. A change of the authority over an account or an asset is a delegate.

### Attributes

The *key* of an address *name*, a code state or a code hash is its *chain* and *party* (and additionally *chain* and *name* for address *name* so neither *party* nor *name* maps inconsistently). The key of a history is (*chain*, *asset*, *party*) for the payer being verified. Every method establishing history MUST identify that payer from wallet-derived context, and a wallet displaying history MUST identify the asset. The *key* of an existing allowance is (*chain*, *asset*, *party*, subject).
The other fields of an attribute are its *value*. A label has no key, as a *party* MAY have several labels.
Two attributes *conflict* if they are of the same type and have equal keys and different values.
Which attributes the wallet uses is the policy of the wallet.

### Correctness

The issuer of a statement, the payment request signer or the issuer of the attestation, is responsible for its correctness, including its canonical encoding and the consistency of its attributes.
The wallet MUST reject a statement which:

* it cannot parse, is not in deterministic CBOR encoding, or has entries not in strictly ascending lexicographic order;
* has duplicate effect keys, a disallowed (entryType, bound) pair, amount != 0 when bound == 3, asset == null when entryType != 0x04, party != h'' when entryType == 0x06, party == h'' when entryType != 0x06, or subject present on 0x02/0x05 or equal to the payer;
* contains invalid UTF-8, non-NFC text, or forbidden control/bidirectional characters in name or label, or non-canonically encoded chains or assets.

It MUST reject the transaction if an attribute which it uses conflicts with another attribute which it is given. It MAY reject a statement which contradicts facts which it knows, such as its trusted metadata.

## Displaying a statement

A wallet which relies on a statement MUST display:

* Every effect, worded as in [Effects](#effects), displaying authority and liability effects (`delegate`, `approve`, `debt`) before transfer and fee effects (`send`, `stake`, `deliver`, `deferred deliver`, `fee`), and preserving encoding order within each group so dust transfers cannot bury critical permissions. An unbounded effect MUST be distinguishable from a bounded one, and a deferred deliver from a deliver.
* The chain of each displayed attribute whose *chain* is not the chain of the transaction being signed.

With signing hash binding, the effects of a transaction attestation account for the whole transaction, including its outputs and its fee. A wallet MAY display these effects in place of its own display of the outputs and the fee of the transaction, so that it displays each transfer once.

The wallet MAY display a title which it derives from the effects, such as "Swap". The wallet MAY display attributes. It MUST NOT display an attribute in place of the address which it describes.
If it displays an attribute established by [state proofs](#state-proofs), it MUST display the time of its block, as given by the block header, so that the payer can judge its freshness.

A wallet without a trusted display, such as an NFC card, MAY instead rely on a statement by a policy which it holds, such as a set of permitted parties and a limit for each asset.
It MUST then rely only on effects which a transaction attestation establishes, MUST evaluate spend and approval limits cumulatively across all effects sharing (chain, asset, subject) so split transfers to multiple parties cannot evade per-asset limits, and MUST NOT sign unless the cumulative and per-party effects satisfy the policy. With payload binding, every output outside the payload other than a change output which it verifies, and the fee which the payer pays, MUST also satisfy the policy.

## Attestation

An attestation is the following array:

```
attestation        = [statement, verificationMethod, attester, verificationData]
verificationMethod = uint .size 4
attester           = bstr
verificationData   = any
```

* *statement*: the attested statement, see [Statement](#statement).
* *verificationMethod*: the 32-bit identifier of the verification method, see [Verification methods](#verification-methods).
* *attester*: the identifier of the trust anchor under which the evidence is verified, see [Evidence](#evidence).
* *verificationData*: the method-specific parameters and evidence, a data item which the method defines.

## Binding

An attestation is bound to a transaction in one of two ways, which its method defines:

* *Payload binding* binds it to the chain, the sender and the outputs whose effects it describes. The attestation remains valid while those outputs are unchanged, so it can be obtained before the fee, the account nonce or the inputs of the transaction are final. The encoding of the outputs is defined only for some chains.
* *Signing hash binding* binds it to the hashes which the wallet signs. The attestation covers the whole transaction, including its fee, and applies to any chain. The wallet needs only the hashes which it signs, so it can be a signer which never receives the transaction, such as an NFC card. Such a signer checks the statement against a policy instead of displaying it. Signing hash binding is not used with a payment request, see [Use with a payment request](#use-with-a-payment-request). Any change of the transaction needs a new attestation. This includes a change of any fact which a signing hash commits to, such as:
  * the fee, such as the gas limit or the fee per gas of an EVM transaction, or a fee bump by replace-by-fee;
  * the account nonce of an EVM transaction;
  * the inputs of a Bitcoin transaction, their sequence numbers, or its locktime;
  * any output, its amount or its script, including a change output;
  * the calldata, the access list or the authorization list of an EVM transaction;
  * the chain ID, or the signature hash type of an input.

### Payload binding

The *payload* of an attestation is the list of outputs whose effects its statement describes, in the order in which they appear in the transaction being signed. With a payment request, these are the requested outputs which are specified by a raw output specification. Otherwise, the application designates them.
The payload need not contain every output of the transaction. The wallet handles every other output and the fee as it would without an attestation, such as by verifying a change output or by displaying the address and the amount of an output.
The wallet computes

```
payloadHash = SHA256([chain, from, [output_1, output_2, ..., output_n]])
```

from the transaction being signed, where:

* *chain*: the chain of the transaction, see [Chains](#chains). The wallet derives it from the transaction, such as from the chain ID of an EVM transaction, and otherwise from the network for which it signs.
* *from*: the account which sends the transaction, a byte string, such as the sender of an EVM transaction, which its unsigned encoding does not contain. The wallet derives it from the key with which it signs. It is empty on a chain where a transaction has no single sender, such as Bitcoin.

Each *output*<sub>*i*</sub> is encoded as follows:

```
output         = evmOutput / utxoOutput
evmOutput      = [value, to, calldataDigest]
utxoOutput     = [outputIndex, amount, scriptPubKey]
value          = uint256
to             = bstr .size 20
calldataDigest = bstr .size 32
outputIndex    = uint
scriptPubKey   = bstr
```

* *value*, *to*: the value and the destination address of an EVM transaction. An EVM transaction which creates a contract cannot be used with payload binding.
* *calldataDigest*: the [ERC-8213](https://github.com/ethereum/ERCs/pull/1639) Calldata Digest of its calldata, keccak256(*len* || *calldata*), where *len* is the byte length of the calldata as a 32-byte big-endian integer. It is present also where the calldata is empty.
* outputIndex, *amount*, `scriptPubKey`: the zero-based output index (vout) in the transaction, the *amount* in the smallest unit, and the `scriptPubKey` of an output of a Bitcoin-like transaction. Binding outputIndex prevents unattested prepended outputs from shifting index-dependent protocol allocations (such as Runes or Ordinals).

Payload binding applies only to Bitcoin-like chains and to EVM chains. On an EVM chain, it applies to the following transaction types, each of which consists of a single call: legacy transactions with an [EIP-155](https://eips.ethereum.org/EIPS/eip-155) chain ID, [EIP-2930](https://eips.ethereum.org/EIPS/eip-2930) transactions (type 1) and [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559) transactions (type 2).

The payload commits to the calldata of an EVM output only by its Calldata Digest. Neither the payload nor the attestation contains the calldata.
A method which interprets or simulates the calldata receives it from elsewhere, such as from the application. The issuer of the attestation MUST check it against the Calldata Digest before it derives the statement.
The wallet computes the Calldata Digest from the transaction being signed, so a different calldata given to the issuer results in a different *attestationHash*.

The issuer of the attestation does not see the rest of the transaction. On a Bitcoin-like chain, the wallet MUST reject payload binding unless every input it signs uses SIGHASH_ALL (or SIGHASH_DEFAULT in BIP-0341) without SIGHASH_ANYONECANPAY, and MUST verify the disposition of any meta-protocol assets within the scope of its policy in the inputs it signs. If the wallet cannot establish their absence or account for them under the method, it MUST reject payload binding. On an EVM chain, the wallet MUST reject a transaction with a part outside its outputs which can have an effect, such as the authorization list of an [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) transaction or the frames of an [EIP-8141](https://eips.ethereum.org/EIPS/eip-8141) transaction. Because a sender account (from) may already hold a persistent [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) delegation on chain even in a type 1 or type 2 transaction, an EVM payload-binding method MUST either cover only calls that cannot invoke from (to != from and no ETH transfer or callback to from) or require the wallet to verify that the sender has *codeState* 0 on the transaction chain. In the latter case the wallet MUST bind the verified state in *methodContext* or verify a state assertion for that sender and nonce. The method MUST state what ensures or is assumed to keep this condition true through execution; a snapshot establishes it only at the verified block.

### Signing hash binding

A *signing hash* is the hash which the chain defines for a signature, such as keccak256 of the unsigned encoding of an EVM transaction, or the signature hash of a Bitcoin input as defined in [BIP-0143](https://github.com/bitcoin/bips/blob/master/bip-0143.mediawiki) or [BIP-0341](https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki). Where the chain's signature scheme signs a raw message without pre-hashing it (such as Ed25519 PureEdDSA on Solana), the *signing hash* in verificationContext is SHA256 of the message; the wallet MUST compute SHA256(message) from the exact message bytes it signs, so a signer which cannot ingest the message bytes cannot sign for such a chain.
The *signing hashes* of a transaction are every signing hash which the wallet signs for it, in the order in which the transaction contains them, such as one for each Bitcoin input which the wallet signs.
Signing hash binding also applies to an off-chain or authorization message whose signature has on-chain security-relevant effects, such as an [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) authorization (keccak256(0x05 || RLP([*chainId*, *address*, *accountNonce*]))) or an EIP-712 typed-data digest (keccak256(0x1901 || domainSeparator || hashStruct(message)), such as Permit2, off-chain intents, or ERC-4337 UserOperations). A method MUST NOT apply to such a message unless its signing hash commits to *chainId* (where replay across chains is possible) and to the verifying contract or protocol. In particular, reject an EIP-7702 authorization with chain ID zero and a replayable EIP-712 authorization without a signed chain identifier. The message is then the transaction to which the attestation is bound.

The issuer of the attestation receives the transaction from the application and derives both its signing hashes and the statement from it. The issuer states the chain of each entry, which a signing hash need not commit to, such as for Bitcoin.
It needs every fact from which the signing hashes and the effects follow, such as the amount and the `scriptPubKey` of each Bitcoin input. It MUST verify such a fact where no signing hash commits to it, such as the amount of a legacy Bitcoin input against its previous transaction.
The wallet computes the signing hashes as it does to sign. A different transaction has different signing hashes, so an attestation for it does not match the *attestationHash* which the wallet computes.

The statement or the set of signing hashes can depend on a fact which no signing hash commits to. For example, the sender of an EVM transaction follows only from its signature, and in a multi-party Bitcoin transaction the transaction alone does not identify which subset of inputs the payer signs; a method which depends on these facts MUST bind them in *methodContext*.
Signing hash binding is not used with a payment request, see [Use with a payment request](#use-with-a-payment-request).

### Transaction attestations and state assertions

An attestation for a method which applies to transactions is a *transaction attestation*, which applies to the transaction to which it is bound. The statement of a transaction attestation has no effects if the transaction, or its payload, has no security-relevant effect. An attestation for a method which applies to state assertions is a *state assertion*, which is bound to no transaction, and whose statement has no effects.
The attributes of a state assertion apply to the transaction whose transaction attestation or payment request has the same nonce, as attributes of its statement.

Without a payment request, the wallet MUST verify every attestation it is given whose verification method it implements. It MUST reject the transaction if any such attestation fails verification, if the transaction attestations differ in binding or in effects, or if a state assertion has a nonce which matches no transaction attestation.

## Verification context

The *verification context* encodes the facts outside the statement which bind the attestation:

```
verificationContext = [nonce, binding, methodContext]
binding             = payloadBinding / signingHashBinding / stateAssertion
payloadBinding      = [0, payloadHash]
signingHashBinding  = [1, hashes]
stateAssertion      = [2]
nonce               = bstr .size (16..64)
payloadHash         = bstr .size 32
hashes              = [+ bstr]
methodContext       = any
```

* *nonce*: an unpredictable challenge of 16 to 64 bytes generated by the wallet with at least 128 bits of cryptographic randomness.
* *payloadHash*: as defined in [Payload binding](#payload-binding). It binds the chain, the sender and the payload of the transaction.
* *hashes*: the signing hashes, in their order.
* *methodContext*: the facts which the verification method defines, or null if it defines none.

The wallet MUST derive *nonce*, *payloadHash*, *hashes* and *methodContext* itself, and not from *verificationData*. *methodContext* contains the other facts which the wallet knows but the issuer cannot derive, such as, with signing hash binding, the sender of an EVM transaction or the signed input indices and change outputs of the payer in a Bitcoin transaction.
The wallet MUST accept only an attestation whose nonce it issued itself and has not invalidated. It MUST invalidate a nonce when it signs a transaction which relies on it, and MAY invalidate a nonce at any other time, such as upon expiry.

## Attestation hash

```
attestationHash = SHA256([h'534c2841', verificationMethod, attester, SHA256(verificationContext), statement])
```

where h'534c2841' is a domain separation tag (this is "SL" followed by 28 in compressed numeric form and "A"), *SHA256*(*verificationContext*) is a 32-byte byte string, and the other elements are those of the attestation.
The wallet computes *attestationHash* itself. *attestationHash* is not transmitted. Evidence such as a signature or a TEE attestation quote commits to it, and the wallet verifies the evidence against the value which it computed.

## Evidence

The evidence in *verificationData* MUST establish every entry of the statement for the verification context, under a trust anchor which the wallet holds for the method. Otherwise, the attestation fails verification.

Evidence which commits to *attestationHash*, such as a signature, a proof or an attestation quote, binds the statement to the transaction, the verification context, the method and *attester*. It establishes the statement only if it commits to the value which the wallet computed.
A method whose evidence is a signature SHOULD encode it as a [COSE_Sign1](https://www.rfc-editor.org/rfc/rfc9052) structure whose payload contains *attestationHash*, so that its header identifies the algorithm, and the wallet verifies it with the same parser as an attestation quote such as that of AWS Nitro Enclaves.
Evidence such as [state proofs](#state-proofs) establishes the entries directly. The wallet checks each entry against the evidence itself, and the trust anchor establishes only the state used for that check.
An attestation quote of a TEE does not protect against an operator with physical access to the platform. A method whose evidence is such a quote MUST accept only evidence which identifies a host of the platform that the operator cannot access.

## Verification methods

A *verification method* determines how the statement is derived and how the attestation is established. Each *verificationMethod* identifies exactly one method, which applies either to transactions or to state assertions.

A method MUST define:

* The transactions or state assertions to which it applies, and for a transaction, its binding.
* The evidence in *verificationData* and the trust anchor which *attester* identifies.
* Its *methodContext*, which MUST determine every other fact known to the wallet which can affect the statement.
* How it establishes the effects and the attributes of the statement.

### Completeness

A *security-relevant effect* is a loss of assets, or a claim on assets or authority over them, now or later, of the payer or of any account whose authority the transaction exercises. A method MUST identify these accounts from the authorized operation, including nested calls made on their behalf. If it cannot account for the effects on each account, it MUST NOT apply.
A method MUST produce a *complete* statement, whose effects account for every security-relevant effect of the payload with payload binding, or of the transaction, including its fee, with signing hash binding.

With signing hash binding, a method MUST account for every part of the transaction which can have an effect, such as the authorization list of an [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) transaction, which delegates the account of each authority to code, or each frame of an [EIP-8141](https://eips.ethereum.org/EIPS/eip-8141) transaction.
A method MUST NOT apply to a transaction with a signing hash which does not commit to every part of the transaction that can affect the payer or such an account, such as that of a Bitcoin input signed with `SIGHASH_NONE`, which commits to no output. A method MUST NOT apply to a transaction whose signing hashes do not commit to its chain where it can be replayed on another chain, such as a legacy EVM transaction without a chain ID.

An effect depends on the transaction alone (*interpretation*), on the transaction executed against an observed state (*simulation*), or on mutable state (*dynamic state*).
An interpretation MUST be bounded under the semantics which the method covers. A simulation MUST be bounded by a condition which transaction validity or execution enforces. Any other effect MUST be stated as unbounded, or as at least 0 for a deliver or a deferred deliver.
For a simulation, the method SHOULD include the identifier of the observed state, such as its block hash, in *verificationData*.

A method MUST define the conditions under which its statement is complete, and the trust assumptions on which it relies, such as that the implementation of a proxy does not change before the transaction is executed. For each bound, and for the absence of every effect which the statement does not contain, the method MUST define what enforces it: the validity of the transaction, its execution under the semantics which the method covers, or a trust assumption. An observed state enforces neither, so a simulation alone establishes neither a bound nor the absence of an effect.

With payload binding, the statement MUST be complete for every value of the parts of the transaction outside the payload which the wallet may sign, such as its EIP-2930 accessList, its gas limit, its fee per gas, its account nonce or its inputs. For example, the effects of an EVM call can depend on the gas limit or pre-warmed accessList gas costs, as a call forwards at most 63/64 of the remaining gas, and the effects of a Runes runestone in a Bitcoin `OP_RETURN` output depend on the inputs and non-payload outputs of the transaction.

A method MUST NOT apply where it cannot meet these requirements.

### Freshness

Each attribute, and each state on which an effect depends, MUST be observed after the nonce is issued, as established by evidence bound to the nonce.
Where the wallet verifies the state itself, as with [state proofs](#state-proofs), the state MUST instead be no older than the latest block which the wallet had verified when it issued the nonce.

### Unknown methods

An attestation for a method which the wallet does not implement establishes nothing, and the wallet ignores it.

### State proofs

With state proofs, the wallet establishes attributes itself, against a state which a trust anchor attests. *verificationData* is a *stateProofs* array:

```
stateProofs  = [rootEvidence, proofs]
rootEvidence = bstr
proofs       = [* bstr]
```

* *rootEvidence* establishes a block of the chain of the attribute, its block timestamp, and its state root (plus receiptsRoot and transactionsRoot where required), under the trust anchor which *attester* identifies, such as a light client checkpoint. Its format is defined by the method, such as SSZ for the Ethereum light client.
* *proofs* prove values under the authenticated roots, each as a byte string, in a tree format which the method defines, such as the account and storage proofs of [EIP-1186](https://eips.ethereum.org/EIPS/eip-1186).

A method MUST NOT state an attribute which its proofs do not establish. For a history state assertion the wallet MUST bind the payer account on the stated chain in *methodContext*.
On EVM chains, the attributes can be proven as follows:

| Attribute | Proof |
| :--- | :--- |
| code state | The account proof of *party*, with its code (verified via streaming keccak256 up to the chain's max code size) where the code hash is neither empty code nor 0x00..00, checking for the exact 23-byte delegation designation (0xef0100 followed by a 20-byte address). |
| code hash | The account proof of *party*, whose code hash is *codeHash* (or proof of non-existence or EIP-161 emptiness for 0x00..00). |
| existing allowance | A storage proof in the token contract, at a slot given by a storage layout which the wallet trusts. |
| address name | On-chain storage proofs of both reverse resolution (*party* -> name via ReverseRegistrar) and forward resolution (ENSIP-15 normalized name -> *party*). Names relying on ERC-3668 OffchainLookup (CCIP-Read) cannot be established by EVM storage proofs alone. |
| label | A storage proof in the registry contract. |
| history | For a direct native payment, verify the signed transaction and successful receipt at the same index against the transaction and receipt roots of a finalized block. Check the sender, destination and positive value. Authenticate the header against the trust anchor, including any ancestor link. For a token or internal transfer, the method MUST also prove the actual transfer of the specified asset from the payer to *party* and the payer’s authorization under the applicable contract semantics. A successful receipt or transfer log alone is insufficient. A single inclusion proof cannot establish a negative history. |

## Use with a payment request

The entries of the statement memo of a [SLIP-0024](slip-0024.md) payment request are claims of the payment request signer, which attestations given with the payment request can establish.
Each such attestation has the nonce of the payment request and is either:

* A transaction attestation with payload binding, whose payload is the requested outputs which are specified by a raw output specification, and whose statement has exactly the effects of the statement of the memo (if a statement memo is present).
* A state assertion.

A payment request uses payload binding. The wallet MUST reject the request if verified transaction attestations disagree on effects, including when there is no statement memo. The wallet handles outputs outside the payload and the fee as it would without an attestation.

The wallet MUST verify every attestation which it is given for a method it implements. It MUST reject the payment request if such an attestation has another nonce, is neither of the above, or fails verification.
A payment request without a statement memo MAY be given transaction attestations (covering its raw output specifications) and state assertions, whose verified entries are displayed as established.

A wallet which has only the signing hashes, such as an NFC card, cannot verify a payment request, as it cannot compute *outputsHash* from the transaction. It MUST reject a payment request.

An entry is *established* as follows:

* The effects of the statement of a transaction attestation for a method which the wallet implements are established.
* An attribute is established by any attestation for a method which the wallet implements and which contains it.

An entry of the memo which is not established is *claimed* by the payment request signer.
The wallet MUST NOT present a claimed entry as established.
Which entries must be established before the wallet signs, and by which methods or by how many attestations, is the policy of the wallet.

The payment request signer MUST NOT sign a payment request whose other memos conflict with its statement memo, such as a coin purchase memo for an amount which the statement does not deliver.

The signed SLIP-0024 statement memo includes the transaction chain. The wallet MUST compare it to the chain for which it signs, even for an empty or attributes-only statement. Every effect other than a deferred deliver MUST be on that chain. Attributes and deferred deliveries on another chain do not change the transaction chain.

The payment request signer is responsible for the statement memo, including the chain of each entry. The wallet enforces what it derives from the transaction being signed: *coinType* and *outputsHash* by the payment request signature, the transaction chain by the signed chain field of the memo, and the chain, the sender and the payload by *payloadHash*.

## Chains

A chain is identified by its [CAIP-2](https://github.com/ChainAgnostic/CAIPs/blob/main/CAIPs/caip-2.md) identifier, serialized as in [CAIP-350](https://github.com/ChainAgnostic/CAIPs/blob/main/CAIPs/caip-350.md):

```
chain     = [chainType, chainRef]
chainType = uint
chainRef  = bstr
```

* *chainType*: the identifier of the CAIP-2 namespace, as defined by its CAIP-350 profile.
* *chainRef*: the chain reference, serialized as defined by that profile.

The CAIP-350 profiles are drafts. This specification fixes the serialization of the following namespaces, and of their accounts, see [Accounts and assets](#accounts-and-assets):

| Namespace | *chainType* | *chainRef* | Account |
| --------- | ----------- | ---------- | ------- |
| `eip155` | 0 | the EIP-155 chain ID as a big-endian unsigned integer without leading zero bytes | the 20-byte address |
| `bip122` | 1 | the first 16 bytes of the genesis block hash, in the order of its hexadecimal string | the `scriptPubKey` |
| `solana` | 2 | the 32-byte genesis block hash | the 32-byte public key |

The `solana` chain reference is the full genesis block hash, as in the examples of [ERC-7930](https://eips.ethereum.org/EIPS/eip-7930). Any other namespace is serialized as defined by its CAIP-350 profile.
The wallet MUST reject a chain whose namespace it does not support, or which is not serialized as defined above.
For example, Ethereum is [0, h'01'], Arbitrum One (chain ID 42161) is [0, h'a4b1'], and Bitcoin is [1, h'000000000019d6689c085ae165831e93'].

A [SLIP-0044](slip-0044.md) coin type does not identify a chain. EVM chains commonly share coin type 60, and coin type 1 is shared by the testnets of all coins.

### Accounts and assets

An account is a byte string, serialized as listed in [Chains](#chains), and otherwise as an address of the CAIP-350 profile of its namespace. For `bip122`, whose profile does not serialize every output script, an account is its `scriptPubKey`.

An asset is a text string, empty ("") for the native asset of the chain. Otherwise, it is the [CAIP-19](https://github.com/ChainAgnostic/CAIPs/blob/main/CAIPs/caip-19.md) asset type without the chain identifier, *asset_namespace*:*asset_reference*, followed by "/" and the canonical base-10 token identifier (ASCII digits without leading zeros, or "0") for a specific token of a non-fungible or multi-token contract. In approve (0x03) and existingAllowanceEntry (0x85), "/" and the token identifier MAY be omitted for a non-fungible or multi-token contract (an approve uses unbounded for a grant or exact zero for a revocation; an existing allowance uses exact 1 for enabled or exact 0 for disabled) to represent collection-wide approval over all tokens of that contract (such as ERC-721 or ERC-1155 setApprovalForAll).
For `eip155`, an address in an asset is a 42-character lowercase hexadecimal string with the prefix 0x, such as "erc20:0xaf88d065e77c8cc2239327c5edb3a432268e5831" or "erc721:0xbc4ca0eda7647a8ab7c2061c2e118a18a936f13d/42". For solana, an SPL token asset uses namespace "spl" and the base58-encoded mint address, such as "spl:EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v".

Accounts on the same chain are equal if and only if their encodings are. An account in an asset, such as the contract of an ERC-20 token, is equal to a *party* which encodes the same address.

## Examples

These examples are informative. They show where the parts of a transaction and the evidence of hypothetical verification methods are placed. The methods, their identifiers and their trust anchors are illustrative and are not registered methods.
The transactions of the examples are [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559) transactions. The data items are written in CBOR diagnostic notation, with comments between slashes. An account such as *P* stands for the byte string of its address, and amounts are written as arithmetic expressions, such as 10^18. An asset such as "erc20:C" stands for the 48-byte text string of the contract address *C*, as defined in [Accounts and assets](#accounts-and-assets).

### Interpretation of a token transfer

The payer *P* transfers 100 USDC to the address *R* on Arbitrum One (chain ID 42161):

* Call: `transfer(R, 100000000)` on the USDC contract *C*.
* Transaction: the destination *C*, the value 0, and 68 bytes of calldata, which consist of the selector `a9059cbb`, *R* left-padded to 32 bytes and be32(100000000).
* Binding: both hypothetical methods use [payload binding](#payload-binding), so the attestation remains valid if the wallet changes the fee.

The hypothetical method reads `transfer(R, x)` as a send of *x* of *C* to *R*:

1. The reading is sound only if *C* behaves as a standard token, which the transaction does not establish.
2. *C* is an upgradeable proxy. Its implementation can change after the attestation is issued and before the transaction is executed, and the transaction does not prevent it.
3. The method therefore covers only contracts in a token list which it trusts. It relies on the trust assumption that, when the transaction is executed, the implementation of each proxy in the list has the semantics which the list states. This includes trust in the administrator of each proxy.
4. The circuit or the enclave fixes the token list, so *attester* binds it, and *attestationHash* includes *attester*.
5. The send is therefore an interpretation under the semantics which the method covers, see [Completeness](#completeness). The gas limit and the fee of the transaction can only make it fail, so the statement is complete under payload binding.

#### Payload

The single output contains the [ERC-8213](https://github.com/ethereum/ERCs/pull/1639) Calldata Digest of the calldata:

```
calldataDigest = keccak256(be32(68) || calldata)
output_1       = [0, C, calldataDigest]
payloadHash    = SHA256([[0, h'a4b1'], P, [output_1]])
```

*payloadHash* covers the chain, Arbitrum One, and the sender *P*. *payloadHash* commits to the Calldata Digest, and *attestationHash* commits to *payloadHash*. The attestation does not contain the calldata. The wallet computes the Calldata Digest, *payloadHash* and *attestationHash* from the transaction being signed, and checks that *C* differs from *P*. The verified method covers only token transfer semantics that cannot invoke *P*.

#### Statement

The statement has a single send effect. The fee is outside the statement, as the method uses payload binding:

```
statement = [
  [0x01, [0, h'a4b1'], "erc20:C", 0, 100000000, R]      / send, exact /
]
```

#### Verification context

Both hypothetical methods interpret the transaction under the semantics of their token list, so *methodContext* is null:

```
verificationContext = [nonce, [0, payloadHash], null]
```

#### Evidence established by a SNARK

* *attester* is the hash of the verifying key of the circuit. The wallet holds the verifying keys it trusts as its trust anchors for the method and selects the one which *attester* identifies.
* *verificationData* is a byte string with the proof.
* The public input of the circuit is *attestationHash*, as field elements, as the circuit defines. The private witness is the calldata, the payload, the verification context and the statement.
* The circuit checks the calldata against its Calldata Digest in the payload and recomputes *attestationHash* from the witness and *attester*. It proves that the method derives the statement from the payload and the calldata.

The wallet verifies the proof under the verifying key, with the *attestationHash* which it computed as the public input.
The proof establishes that the derivation was correct. It does not establish that *C* behaves as the token list states, which remains a trust in the method.

#### Evidence established by an AWS Nitro enclave

* *attester* is PCR0 of the enclave, the 48-byte SHA-384 hash of its enclave image, which contains the code which derives the statement. The trust anchors of the method are the AWS Nitro Enclaves root certificate and the values of PCR0 which the wallet accepts.
* *verificationData* is the attestation document of the enclave, a COSE_Sign1 structure signed with ECDSA P-384, whose `user_data` begins with *attestationHash*.

The wallet verifies the attestation document in these steps:

1. The certificates of `cabundle`, from the root certificate which the wallet holds.
2. The certificate of the enclave, against the last certificate of `cabundle`.
3. The signature of the attestation document, under the certificate of the enclave.
4. PCR0 equals *attester*, and the wallet accepts *attester*. A debug enclave has PCR0 of zeros, which the wallet does not accept.
5. `user_data` begins with the *attestationHash* which the wallet computed.

A wallet without a real-time clock checks that no certificate's notAfter timestamp precedes the wallet's monotonic time floor (the maximum of its firmware build time and the timestamp of the latest verified block header it has observed), bounding exposure to historically compromised ephemeral enclave certificates while relying on the nonce for freshness.

AWS hosts the enclave, so its operator has no physical access to the platform, see [Evidence](#evidence).

In both methods, *attestationHash* includes *attester*, so the evidence cannot be presented under another trust anchor.

The wallet displays the send, and the fee as it would without a statement:

```
Send 100 USDC to R
```

### Simulation of a token swap

The payer swaps 1 ETH for USDC on Ethereum (chain ID 1) through the Uniswap V2 router *U*, by calling `swapExactETHForTokens(2450000000, [WETH, T], P, deadline)`, where *T* is the USDC contract and *P* is the payer's address.
The transaction has the destination *U*, the value 10<sup>18</sup> wei, 228 bytes of calldata, and a maximum fee of 0.002 ETH.
The statement is derived and attested by a simulation provider which executes the transaction against the state of the chain. Its method uses [signing hash binding](#signing-hash-binding), so the statement covers the whole transaction, including the fee. The wallet signs the single signing hash *H* = keccak256(0x02 || RLP of the unsigned transaction).

#### Statement

The provider executes the transaction against a state observed after it receives the nonce. In that state, the swap would deliver, for example, 2503.17 USDC to *P*. The state can change before the transaction is included, so that amount is not enforced and MUST NOT be stated as the bound.
The router computes the amount of *T* from the reserves of the pool and reverts if it is less than the `amountOutMin` argument, 2450 USDC. The pool then transfers that amount to *P*. *P* receives exactly that amount, because *T* takes no fee on transfer and has no transfer hooks. Execution enforces this condition, so the bound of the deliver effect is 2450 USDC.
The validity of the transaction enforces the bound of the send effect, as the transaction transfers exactly its value, and the bound of the fee.
The method covers only the router *U*, whose code is immutable, and tokens in a token list which it trusts. *T* is an upgradeable proxy, so the method relies on the same trust assumption as the first example. Under the code of *U* and of *T*, `swapExactETHForTokens` grants no approval and transfers nothing from *P* other than the value of the transaction. This, not the simulation, establishes that the transaction has no other security-relevant effect. The simulation observes a single state.

```
statement = [
  [0x01, [0, h'01'], "", 0, 10^18, U],                  / send, exact /
  [0x02, [0, h'01'], "erc20:T", 1, 2450000000, P],      / deliver, at least /
  [0x06, [0, h'01'], "", 2, 2 * 10^15, h'']             / fee, at most /
]
```

The wallet displays:

```
Send 1 ETH to U
Deliver at least 2450 USDC to P
Pay a fee of at most 0.002 ETH
```

#### Verification context

The execution of the transaction depends on its sender, which the wallet knows but the unsigned transaction does not contain. The method therefore defines *methodContext* as the byte string of the 20-byte address of the sender:

```
verificationContext = [nonce, [1, [H]], P]
```

The observed state is not part of the verification context, as the wallet cannot derive it. Its freshness follows from the nonce, which the provider receives before it observes the state.

#### Evidence established by a provider signature

* *attester* is the public key of the provider, such as a 32-byte Ed25519 public key. The wallet holds the public keys of the providers it trusts as its trust anchors for the method.
* *verificationData* is a COSE_Sign1 structure, signed by the provider with EdDSA, whose payload is the encoding of [*attestationHash*, *blockHash*]. *blockHash* is the 32-byte hash of the block whose state the provider observed.

The wallet verifies the COSE_Sign1 signature under the public key which *attester* identifies, and checks that the payload contains the *attestationHash* which it computed.
The signature also covers *blockHash*, which is not part of *attestationHash*.
Unlike a SNARK or a TEE, the signature establishes only that the provider made the statement. The wallet trusts the provider both to derive the statement correctly and to observe the state after the nonce is issued.

### State proof of a code state

With the swap of the previous example, the application gives a state assertion that the router *U* is controlled by code. The state assertion has the same nonce as the swap. The wallet establishes it itself by [state proofs](#state-proofs). Its light client for Ethereum had verified the block *B*<sub>0</sub> when the wallet issued the nonce.

#### Statement and verification context

```
statement = [
  [0x83, [0, h'01'], U, 1]                              / code state: code /
]
```

A state assertion is bound to no transaction. The method has no *methodContext*, so it is null:

```
verificationContext = [nonce, [2], null]
```

#### Evidence established by state proofs

* *attester* identifies the checkpoint from which the light client of the wallet was bootstrapped, such as the root of a finalized beacon block. It is only the bootstrap anchor of the light client.
* *rootEvidence* is the chain of sync committee updates from the latest period which the wallet has verified, the header of a finalized block *B*<sub>1</sub>, and the proof of the state root of *B*<sub>1</sub> in its header.
* *proofs* is the [EIP-1186](https://eips.ethereum.org/EIPS/eip-1186) account proof of *U* under the state root of *B*<sub>1</sub>, followed by the code of *U*.

The wallet verifies *rootEvidence* with its light client and checks that *B*<sub>1</sub> is not earlier than *B*<sub>0</sub>. This establishes that the state is not older than the light client was when the wallet issued the nonce. It does not establish that the state was observed after the nonce, see [Freshness](#freshness).
The wallet then verifies the account proof under the state root of *B*<sub>1</sub> and checks the code against the code hash of the account.
Finally, it checks that the code is not empty and does not begin with 0xef0100. This establishes that *U* is controlled by code and is not a delegation.
The evidence establishes the entry directly, and no party signs *attestationHash*. The wallet relies on its light client and on the honesty of the sync committee, not on an issuer of the attestation.

The attribute applies to the swap, whose attestation has the same nonce. The wallet displays it next to *U*:

```
Send 1 ETH to U
   U has code (as of block B1, 2026-10-30 12:00 UTC)
Deliver at least 2450 USDC to P
Pay a fee of at most 0.002 ETH
```

### Payment request with established and claimed entries

A merchant requests the payment of the first example by a [SLIP-0024](slip-0024.md) payment request for Arbitrum One, with the recipient name "Shop", *coinType* 60, the nonce issued by the wallet, and a statement memo with chain [0, h'a4b1'] and statement:

```
statement = [
  [0x81, [0, h'a4b1'], R, "shop.eth"],                  / address name /
  [0x01, [0, h'a4b1'], "erc20:C", 0, 100000000, R]      / send, exact /
]
```

The application gives no transaction attestation, so the send effect and the address name are claimed by the merchant, who signed the payment request. The application does give a state assertion with the nonce of the payment request. It is established by a provider signature, as in the second example, under a method for state assertions:

```
statement = [
  [0x83, [0, h'a4b1'], R, 0]                            / code state: keys only /
]
```

The wallet verifies the state assertion. The code state is established, although the memo does not contain it. The wallet displays the fee as it would without a statement, and:

```
Pay to Shop                        (recipient name)
Send 100 USDC to R                 claimed by the merchant
   shop.eth is R                   claimed by the merchant
   R has no code                   established
```

Whether the wallet signs depends on its policy. A wallet which requires established effects rejects this payment request. The application can then add a transaction attestation, such as that of the first example with the nonce of the payment request. Its payload is the requested output, and it establishes the send.

### Interpretation of a bridge transfer

The payer moves 1 ETH from Ethereum to its address *P* on Scroll (chain ID 534352), a zk rollup:

* Call: `depositETH(P, 10^18, gasLimit)` on the Scroll bridge contract *G* on Ethereum.
* Transaction: the destination *G*, the value 10<sup>18</sup> + *f* wei, and 100 bytes of calldata.
* Execution fee on Scroll: *f* pays for the execution of the deposit on Scroll. The bridge refunds any unused part of *f* to the payer (requiring P's codeState == 0 under payload binding so the ETH refund cannot trigger delegated code), so the payer sends at most 10<sup>18</sup> + *f*.

The payment on Ethereum is made by the execution of the transaction. The delivery on Scroll is made later by the rollup, which executes the deposit and proves it on Ethereum by a validity proof. The delivery is therefore a deferred deliver.
The hypothetical method interprets calls to *G* under the semantics of the bridge, with payload binding. The bound of the deliver is the amount in the calldata, which the rollup delivers exactly.
If the execution on Scroll fails, the deposit can be replayed, and the asset stays locked in the bridge until it succeeds. The asset is never released to another party, so the deliver holds only if it completes.

#### Payload and statement

```
calldataDigest = keccak256(be32(100) || calldata)
output_1       = [10^18 + f, G, calldataDigest]
payloadHash    = SHA256([[0, h'01'], P, [output_1]])
```

```
statement = [
  [0x01, [0, h'01'], "", 2, 10^18 + f, G],              / send, at most /
  [0x05, [0, h'082750'], "", 0, 10^18, P]               / deferred deliver, exact /
]
```

*payloadHash* binds the chain Ethereum and the sender *P*. The wallet verifies a fresh account proof for *P* on Ethereum at block *B*, establishes *codeState* 0 and derives *methodContext* as [*P*, 0, *B*], where *B* is the verified block hash. The method assumes *P* remains undelegated until execution. If the wallet cannot establish the initial state or its policy does not accept that assumption, it rejects the attestation. The verification context is:

```
verificationContext = [nonce, [0, payloadHash], [P, 0, B]]
```

The evidence is established as in the first example, with a method which covers *G*. For *f* of 0.0001 ETH, the wallet displays:

```
Send at most 1.0001 ETH to G
Deliver 1 ETH to P on Scroll, later
```

The payer can tell the deferred deliver from a deliver, and its chain from that of the transaction.

Trust in the method includes trust in the verifier of the rollup on Ethereum, in the consensus of Ethereum, and in the liveness of the rollup.
The deliver needs that liveness to complete, and the enforced inclusion of transactions from Ethereum supports it.
With a bridge whose operator attests the transfer, such as Circle's CCTP, the statement has the same form, and trust in the method includes trust in that operator.

### Approval and swap in one call

The payer swaps 2500 USDC for ETH on Ethereum through a router *U* in one call:

* Permit: the call also carries a [Permit2](https://github.com/Uniswap/permit2) permit, signed by the payer, which allows *U* to spend any amount of USDC (*T*).
* The wallet evaluates the Permit2 signature when it signs the EIP-712 digest, since a holder can submit the permit separately. The later swap attestation cannot authorize that earlier signature retroactively.
* Approval: the approval outlasts the transaction, so it is a security-relevant effect of its own. The approval is stated as unbounded and as if it does not lapse.
* Binding: the method uses signing hash binding, so the statement includes the fee.

The statement is:

```
statement = [
  [0x01, [0, h'01'], "erc20:T", 0, 2500000000, U],      / send, exact /
  [0x02, [0, h'01'], "", 1, 99 * 10^16, P],             / deliver, at least /
  [0x03, [0, h'01'], "erc20:T", 3, 0, U],               / approve, unbounded /
  [0x06, [0, h'01'], "", 2, 2 * 10^15, h'']             / fee, at most /
]
```

The wallet displays:

```
Allow U to spend any amount of USDC
Send 2500 USDC to U
Deliver at least 0.99 ETH to P
Pay a fee of at most 0.002 ETH
```

### Swap and payment to a merchant

A merchant *M*, with the recipient name "Shop", requests 2400 USDC by a payment request. The payer pays with 1 ETH through an aggregator *A*. The aggregator swaps the ETH, pays exactly 2400 USDC to *M* and returns the rest, at least 0.01 ETH, to the payer. The call to *A* is the requested output, and the statement memo specifies chain [0, h'01'] and the following statement:

```
statement = [
  [0x01, [0, h'01'], "", 2, 99 * 10^16, A],            / net send, at most /
  [0x02, [0, h'01'], "erc20:T", 0, 2400000000, M]       / deliver, exact /
]
```

The effects describe the payment completely. A transaction attestation with payload binding, by a method which covers *A*, has exactly these effects and establishes them. The code of *A* transfers the amount in its calldata to *M* and reverts unless it returns at least 0.01 ETH to *P*. The method requires the same verified sender code state and execution-time assumption as the bridge example. Under those conditions the refund bounds the net send to 0.99 ETH.
The wallet displays the fee as it would without a statement, and:

```
Pay to Shop                        (recipient name)
Send at most 0.99 ETH to A         established
Deliver 2400 USDC to M             established
```

### Supply and borrow

The payer supplies 10 ETH to a lending pool *L* on Ethereum and borrows 15000 USDC (*T*) against it in one call. The pool delivers 10 of its receipt token *W* to the payer.
The loan gives the pool a claim on the payer, which it can enforce by liquidating the collateral. This claim is a debt effect. It is stated as at least the borrowed amount, as interest accrues. The method uses signing hash binding, so the statement includes the fee:

```
statement = [
  [0x01, [0, h'01'], "", 0, 10^19, L],                  / send, exact /
  [0x02, [0, h'01'], "erc20:W", 0, 10^19, P],           / deliver, exact /
  [0x02, [0, h'01'], "erc20:T", 0, 15000000000, P],     / deliver, exact /
  [0x06, [0, h'01'], "", 2, 3 * 10^15, h''],            / fee, at most /
  [0x08, [0, h'01'], "erc20:T", 1, 15000000000, L]      / debt, at least /
]
```

The two delivers are in the order of the encodings of their assets, which here assumes that *W* sorts before *T*. The wallet displays:

```
Owe at least 15000 USDC to L
Send 10 ETH to L
Deliver 10 aWETH to P
Deliver 15000 USDC to P
Pay a fee of at most 0.003 ETH
```

### Wallet without a display

An NFC card signs the swap of the second example. It has no display, and the phone, which relays its messages, is not trusted. The card receives the signing hash *H* of the transaction, but not the transaction.
The card holds a policy, which permits, on Ethereum, a send of at most 2 ETH to a party in a list which contains *U*, any deliver to the payer *P*, a fee of at most 0.01 ETH, and no other effect. It also holds the public key of the simulation provider as the trust anchor of its method.

The card issues a nonce, which the phone sends to the provider with the transaction.
The provider computes *H* from the transaction, derives the statement of the second example, and signs *attestationHash* over the verification context of the second example.
The phone gives the card *H* and the attestation. The card derives the verification context from its nonce, *H* and its own address *P*, and computes *attestationHash*.
It verifies the signature under the public key of the provider. It then checks the effects against its policy. The send of 1 ETH to *U*, the deliver of at least 2450 USDC to *P* and the fee of at most 0.002 ETH are permitted, so it signs *H* and invalidates the nonce.

If the phone gives the card the signing hash of another transaction, the *attestationHash* which the card computes does not match the one which the provider signed, and the card does not sign.
If the phone gives the provider a transaction with a higher fee, the provider states that fee, and the card refuses it if it exceeds the policy. An unbounded approve, an effect stated on another chain, or any other effect which the policy does not permit, also makes the card refuse.

The attestation can also come from an enclave, whose measured code derives the statement and verifies any state which it uses. The card then trusts the code and the host of the platform, not the operator of the enclave.
The quote of the enclave is verified either on the card, where the evidence needs no collateral of the TEE vendor, such as with AWS Nitro Enclaves, or when the card is provisioned, for a signing key which the enclave generates and does not export. In the latter case, the card holds the public key of the enclave as the trust anchor, and verifies the attestation as a signature.

#### Interpretation in an AWS Nitro enclave

An AWS Nitro enclave interprets the transaction and its calldata. An operator runs the enclave, but AWS hosts it, so the operator has no access to its memory or to its platform.

The hypothetical method interprets calls to the Uniswap V2 router *U* under its semantics, for tokens in a token list which it trusts, with signing hash binding. The method does not apply to any other contract. The enclave image fixes the semantics of *U* and the token list, so *attester* binds them, as in the first example.

The enclave computes *H* from the transaction and decodes the calldata of `swapExactETHForTokens`. The enclave then derives each effect of the second example:

* Send 1 ETH to *U*: the value of the transaction.
* Deliver at least 2450 USDC to *P*: the calldata sets `amountOutMin` to 2450 USDC and the recipient to *P*. Under the semantics of *U*, the transaction either transfers at least `amountOutMin` of *T* to the recipient or reverts. *T* is in the token list, so *T* takes no fee on transfer and has no transfer hooks, under the trust assumption of the first example.
* Pay a fee of at most 0.002 ETH: the maximum fee of the transaction.

None of the effects depends on the sender, so *methodContext* is null:

```
verificationContext = [nonce, [1, [H]], null]
```

*attester*, the trust anchors and *verificationData* are as in [Evidence established by an AWS Nitro enclave](#evidence-established-by-an-aws-nitro-enclave), and `user_data` begins with *attestationHash*.

The card trusts AWS as the vendor and as the host of the platform, and the code which PCR0 measures, including its token list. Unlike with a provider signature, the card does not trust the operator. The worst the operator can do is withhold the attestation.

## Appendix: Comparison of bindings

This appendix is informative.

| Property | Payload binding | Signing hash binding |
| :--- | :--- | :--- |
| What the attestation covers | the payload; the wallet handles the fee and the other outputs | the whole transaction or signed message, including the fee |
| A change of the fee, the account nonce or the inputs | the attestation remains valid | needs a new attestation |
| A signer which only signs hashes, such as an NFC card | no | yes, on chains whose signature scheme signs a hash |
| A payment request | yes | no |
| EIP-7702 authorization lists, EIP-8141 frame transactions, and EIP-712 messages | no, the wallet rejects them | yes, if the method accounts for them |
| Chains | EVM and Bitcoin-like chains, whose outputs it encodes | any chain |

Payload binding suits an attestation obtained before the transaction is final, such as with a quote, a payment request or for a PSBT. Signing hash binding suits a wallet which relies on a policy, off-chain typed-data authorizations, and a signer which only signs hashes.
