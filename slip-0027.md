## Abstract

This document defines how key pairs of cryptographic schemes are generated from [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) nodes, together with a registry of currently supported schemes.

## Motivation

The standardization of post-quantum cryptography has created a need to derive the inputs to the key generation of schemes such as ML-DSA ([FIPS 204](https://doi.org/10.6028/NIST.FIPS.204)) and SLH-DSA ([FIPS 205](https://doi.org/10.6028/NIST.FIPS.205)) deterministically from a single master secret, so that a wallet can be restored from its backup.

[BIP 32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki) and [SLIP 10](https://github.com/satoshilabs/slips/blob/master/slip-0010.md) derive a hierarchy of key pairs in a way that supports public derivation. For the elliptic-curve schemes they cover, child public keys can be derived from parent public keys without access to the corresponding private keys. This is possible because of the homomorphism between scalar addition and point addition that elliptic-curve schemes provide. Schemes without such structure, including all current post-quantum signature standards, do not admit public derivation. For these schemes it is simpler to derive the inputs to the key generation as [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) secret keys and let the key generation of the scheme produce the key pair. This works in the same way for every scheme, without any arithmetic specific to the scheme.<sup>[1](#1-extension-of-slip-21-rather-than-slip-10)</sup>

## Key pair generation

For a [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) node *N*, Key(*N*) denotes its 32-byte secret key as defined in SLIP 21.

A *scheme label* is the label which identifies a cryptographic scheme with a specific parameter set, as listed in the registry below. A *key pair* is the output of the key generation function of a scheme. An *input value* is an input to that function, derived at a path of the form:

```
m / <context labels> / <scheme label> / <key pair labels> / <input labels>
```

where the *context labels* and *key pair labels* are defined by the specification of the application in accordance with SLIP 21 and the *input labels* are the sequence of labels assigned to the input value in the registry. Every input value currently in the registry has a single input label. The context labels are not empty, while the key pair labels may be.

An input value is Key(*N*)[0:*length*], where *N* is the node at the path specified above<sup>[2](#2-input-values-as-child-nodes)</sup> and *length* is its length in bytes as given in the registry.<sup>[3](#3-longer-and-range-restricted-input-values)</sup>

The scheme label is subject to the following rules:

1. The scheme label MUST be a level of its own, i.e., it MUST NOT encode any other parameter.<sup>[4](#4-position-of-the-scheme-label)</sup>
2. A path MUST contain exactly one scheme label. The specification of the application MUST determine the level of the scheme label from the labels which precede it.<sup>[5](#5-uniqueness-of-input-values)</sup>
3. A context label or key pair label SHOULD NOT coincide with a scheme label listed in the registry.<sup>[4](#4-position-of-the-scheme-label)</sup>
4. The scheme label SHOULD be placed:
    * below any label which restricts the schemes used beneath it, such as a script type,
    * below any label whose nodes may need to be provided to another party as a whole, such as an account, and
    * above the labels which only enumerate key pairs of the scheme, such as an address index.<sup>[4](#4-position-of-the-scheme-label)</sup>

The columns have the following meaning:

**Scheme label.** Braces in a scheme label list alternatives, so that one row of the table describes several schemes. For example, `SLH-DSA-{SHA2,SHAKE}-128{s,f}` describes the four schemes with the labels `SLH-DSA-SHA2-128s`, `SLH-DSA-SHA2-128f`, `SLH-DSA-SHAKE-128s` and `SLH-DSA-SHAKE-128f`.<sup>[7](#7-scheme-labels)</sup> The scheme labels of XMSS<sup>MT</sup> contain the character "/", which is part of the label and not a separator of the path. The LMS scheme label combines the LMS parameter set with the Winternitz parameter *w* of the LM-OTS parameter set, since [SP 800-208](https://doi.org/10.6028/NIST.SP.800-208) requires the two to use the same hash function and output length. For example, `LMS_SHA256_M32_H10_W4` denotes `LMS_SHA256_M32_H10` with `LMOTS_SHA256_N32_W4`.

**Input labels.** The input values of a scheme are those which the standard of the scheme requires to be generated by a random bit generator for the key generation algorithm identified in the Usage column, whether the algorithm takes them as arguments or generates them itself, including values which become part of the public key. Their input labels are the names used in that standard, copied verbatim, except that a name which is not ASCII is replaced by the name the standard uses for it, as in `"seed"` for *ξ*.<sup>[8](#8-input-labels)</sup>

**Length.** The length of each input value in bytes. Where the column lists several values, they apply to the input labels in order.

**Nominal strength.** The security strength in bits for which the parameter set is designed, which its standard also requires of the random bit generator used in key generation. The security strength of a key pair is the smaller of its nominal strength and the entropy of the master secret. An application MUST NOT claim a security strength for a key pair which exceeds the entropy of the master secret. A scheme whose nominal strength exceeds that entropy may nevertheless be used, for example to retain a margin against advances in the cryptanalysis of the scheme.

**Usage.** The key generation algorithm of the scheme and how it interprets the input values.

### Stateful schemes

XMSS, XMSS<sup>MT</sup> and LMS are stateful. An application using a stateful scheme MUST ensure that no one-time key signs more than one message, including after restoration from backup. How the application does so is outside the scope of this specification.<sup>[9](#9-stateful-schemes)</sup>

### Adding schemes

Future schemes are added by extending the table. The input labels of a scheme MUST be suffix-free, i.e., the sequence of labels assigned to one input value MUST NOT end in the sequence assigned to another input value of the same scheme.<sup>[5](#5-uniqueness-of-input-values)</sup>

A hybrid scheme whose specification defines a key generation function, such as X-Wing, SHOULD be added as a scheme of its own, whose input values are those of that function. A construction which combines independently generated key pairs, such as a composite signature or an HSS hierarchy of LMS key pairs, SHOULD NOT be added. The application derives its key pairs at paths of its choosing.<sup>[10](#10-composite-schemes)</sup>

## Encoding of integer labels

When an integer is used as a path label, it MUST be encoded as its shortest possible decimal ASCII representation.<sup>[11](#11-encoding-of-integer-labels)</sup> Specifically:

* The integer MUST be non-negative.
* The encoding consists of the ASCII digits 0 to 9 only.
* No leading zeros are permitted, except that the integer 0 is encoded as `"0"` (the single byte 0x30).

This encoding matches the convention of [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md). Applications requiring signed or otherwise structured indices may define their own encoding, provided it is documented in the application's specification and encodes every non-negative integer as specified above.

## Example paths

The path of the seed *ξ* of an account on an account-based chain, here [SLIP 44](https://github.com/satoshilabs/slips/blob/master/slip-0044.md) coin type 60 (Ether), account index 2, where SLIP 9999 stands for the specification of the application:

```
m / "SLIP-9999" / "60" / "2" / "ML-DSA-44" / "seed"
```

The path of SK.seed of an address on a UTXO-based chain, here coin type 0 (Bitcoin), account index 2, script type P2MR, internal chain (change) 1, address index 14:

```
m / "SLIP-9999" / "0" / "2" / "p2mr" / "SLH-DSA-SHAKE-128s" / "1" / "14" / "SK.seed"
```

The paths of SK.prf and PK.seed differ only in the last label.

The context labels and key pair labels are illustrative. Their structure is defined by the specification of the application.

## Test vectors

The test vectors are given in [`slip-0027/vectors.json`](slip-0027/vectors.json), which is generated by [`slip-0027/testvectors.py`](slip-0027/testvectors.py). All of them use the master secret

```
S = c76c4ac4f4e4a00d6b274d5c39c700bb4a7ddc04fbc6f78e85ca75007b5b495f74a9043eeb77bdd53aa6fc3a0e31462270316fa04b8c19114c8798706cd02ac8
```

which is the [BIP 39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki) seed of the mnemonic "all all all all all all all all all all all all" with an empty passphrase.

The file contains a list of test vectors, one for each key pair, with the following fields:

* `description`: A description of the test vector.
* `path`: The labels of the path, without the input labels.
* `scheme`: The scheme label, which also occurs in `path`.
* `input_values`: The input values in hexadecimal, indexed by their input labels.
* `public_key_hash`: The SHA-256 hash in hexadecimal of the public key which the key generation function of the scheme produces from the input values. This field is omitted for XMSS, XMSS<sup>MT</sup> and LMS.

## Design rationale

### 1. Extension of SLIP 21 rather than SLIP 10

The alternative we considered was to add each post-quantum scheme to [SLIP 10](https://github.com/satoshilabs/slips/blob/master/slip-0010.md) in the way ed25519 was added, with a new master key string and hardened derivation only. We rejected it for the following reasons.

(a) In SLIP 10 the scheme is selected at the root of the tree. Each scheme has a master key of its own, so a single node never determines key pairs of more than one scheme. An application which uses several schemes cannot provide an account to another party as one node. See item [4](#4-position-of-the-scheme-label).

(b) In SLIP 10 the private key of a node is both the key used by the application and the only secret which enters the derivation of its children. The chain code enters the derivation as well, but it is serialized alongside the public key and is routinely exported. Thus, if the private key of a node leaks, so does the entire subtree beneath it. In [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) the first half of a node is used only to derive children and the second half is used only as the secret key of that node. A leaked secret key never compromises the child nodes of its node.

(c) The chain code of SLIP 10 has no remaining purpose. In [BIP 32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki) the chain code exists so that the public key of a node does not by itself allow anyone to derive its child public keys. Deriving them requires the chain code as well. For a scheme that does not admit public derivation there is nothing for it to do. What remains of the BIP 32 structure, the chain code, the zero byte padding the private key to 33 bytes and the retry step in master key generation, is carried along without serving any function.

(d) In the hardened derivation of SLIP 10 the private key enters HMAC-SHA512 as the message and the chain code as the key, an arrangement inherited from non-hardened derivation, where the chain code is the only secret. In SLIP 21 the secret enters HMAC-SHA512 as the key and the public label as the message, as explained in its [design rationale](https://github.com/satoshilabs/slips/blob/master/slip-0021.md#child-node-derivation). The arrangement of SLIP 10 has two drawbacks:

* For an adversary who holds the chain code, it relies on HMAC being a pseudorandom function when keyed through its message. This is not implied by the conventional PRF security of HMAC, and its proof requires additional assumptions [BBGS23].
* HMAC processes its key in a block of its own, apart from data chosen by the attacker. In SLIP 10 this isolation is spent on the chain code, while the private key shares a block with the index, which is no better than a plain hash of the concatenation.

Neither of these drawbacks is a weakness that an attacker can exploit.

Since the schemes do not admit public derivation, either route yields a tree of hardened derivations only, and the choice is one of structure.

### 2. Input values as child nodes

Each input value is the secret key of its own SLIP 21 node rather than a slice of a single expanded output. We considered defining a function which expands the secret key of a node to an arbitrary length, in the manner of the counter mode of [NIST SP 800-108](https://doi.org/10.6028/NIST.SP.800-108r1-upd1), and taking the input values from consecutive bytes of its output. The two constructions are equivalent under the assumption that HMAC-SHA512 is a pseudorandom function, but the child node construction has the advantage that it introduces no new operation on SLIP 21 nodes, so that every input value is the secret key of a SLIP 21 node, and it requires no table of byte offsets, since the name of the input value is its label.

### 3. Longer and range-restricted input values

The schemes currently in the registry impose no restriction on the content of their input values and require at most 32 bytes for each one, so the secret key of a single node always suffices. How to derive longer or restricted input values will be defined when a scheme in the registry needs them. We envisage appending integer labels to the input label, as in `<input label> / <retry> / <block>`. The retry counter is incremented whenever the scheme rejects a value, and the secret keys of consecutive blocks are concatenated and truncated to the required length. A scheme which needs only one of the two counters would use only that one. This is why the input labels of an input value are defined as a sequence. The extension remains within SLIP 21 and requires no change to the existing rows of the registry.

### 4. Position of the scheme label

The position of the scheme label is left to the specification of the application. A node determines all nodes beneath it, so the position decides which sets of key pairs can be provided to another party as a single node. For example, an application which places the scheme label below the coin type can provide all key pairs of one coin across all schemes, or those of one scheme only.

The recommended position follows from two considerations. Firstly, a node can determine key pairs of several schemes only if it is above the scheme label. This applies to an account, which may need to be provided to another party as a whole, and to a script type, which determines the scheme or the fixed set of schemes used for its addresses and whose key pairs are discovered together. A scheme can then also be added to the application without creating a second such node. Secondly, the labels which only enumerate key pairs should be below the scheme label, so that the scheme node is derived once and the scheme label does not cost an additional HMAC-SHA512 computation for every key pair. At this position the scheme label costs one HMAC-SHA512 computation per script type of an account, even where the script type determines a single scheme and the label is redundant.

The opposite order, with the scheme label below an enumerating label, makes sense where key pairs of several schemes are used together and the node which determines them may need to be provided to another party, for example a single address whose script contains keys of several schemes. The scheme label then costs an additional HMAC-SHA512 computation for every key pair.

We considered fixing the scheme label at the first level, in the manner of SLIP 10, where each curve has a tree of its own. However, an application would then have been unable to provide all of its key pairs as a single node.

The scheme label is required to be a level of its own even in an application which uses a single scheme, where SLIP 21 would recommend combining it with a neighbouring fixed parameter. This keeps the scheme recognizable in every path. For the same reason a scheme label is discouraged at any other level.

### 5. Uniqueness of input values

No path may have two interpretations, since the node at a path can hold only one input value. Two kinds of ambiguity have to be excluded. Firstly, a path must not be readable as belonging to two schemes. Otherwise the same node could hold an input value of two schemes, which would then generate a key pair under each. This is excluded because a path contains exactly one scheme label at a level determined by the labels which precede it.

Secondly, a path must not be readable as two input values of the same scheme. Were the input labels of one input value to end in those of another, a path ending in the longer sequence could also be read as ending in the shorter one, with the remaining labels taken as key pair labels. This is why the input labels of a scheme are required to be suffix-free.

If the path of a key pair happens to end in an input label, the node at that point holds an input value and is also the parent of further nodes. The two roles use the two halves of the node, the first for the derivation of child nodes and the second as the secret key, so there is no conflict.

### 6. Entropy of the master secret

[FIPS 203](https://doi.org/10.6028/NIST.FIPS.203), [FIPS 204](https://doi.org/10.6028/NIST.FIPS.204), [FIPS 205](https://doi.org/10.6028/NIST.FIPS.205) and SP 800-208 require the random bit generator used in key generation to have at least the nominal strength of the parameter set. The analogue in this specification is the entropy of the source of the master secret, typically a mnemonic, which the derivation cannot verify.

This specification does not require a minimum number of mnemonic words for a scheme. A 12-word [BIP 39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki) mnemonic or a 20-word [SLIP 39](https://github.com/satoshilabs/slips/blob/master/slip-0039.md) share provides 128 bits of entropy. An application may use it with ML-DSA-65 and claim a security strength of 128 bits, but not of 192 bits. Requiring 18 words for ML-DSA-65 would forbid this configuration, although a parameter set above the claimed strength is a legitimate choice, as X-Wing [BCD+24] shows by combining ML-KEM-768 with X25519 for a security strength of 128 bits.

A passphrase cannot be counted, since its entropy is unknown. In SLIP 39 it does not increase the entropy at all, since the passphrase only encrypts the master secret, which therefore has exactly the entropy it was generated with.

### 7. Scheme labels

Each scheme label is the canonical FIPS or RFC spelling of the scheme, including the parameter set (e.g., `ML-DSA-44` rather than `ML-DSA`). Different parameter sets are different schemes, so applications deriving at the same path always agree on the parameters, and input values are never shared between parameter sets. Sharing them would be unsafe for hash-based schemes in particular, since their one-time keys are derived from the input values by address and two tree shapes can collide on an address. A row with braces is only shorthand for several rows whose other entries are identical.

### 8. Input labels

The input values of a scheme are determined by a single criterion, so that adding a scheme to the registry involves no choice. Values which become part of the public key, such as PK.seed of SLH-DSA, SEED of XMSS and I of LMS, are included because the key pair cannot be restored from backup without them. The input labels are copied from the standard, so that a registry row reads as the interface of the key generation algorithm it refers to.

### 9. Stateful schemes

XMSS, XMSS<sup>MT</sup> and LMS take input values of the same kind as SLH-DSA, which are derived in the same way. However, unlike that of SLH-DSA, their security depends on never signing twice with the same one-time key, and the state which prevents this cannot be derived from the master secret. A wallet restored from its backup holds the key pair without the state. Managing the state is left to the application.

[SP 800-208](https://doi.org/10.6028/NIST.SP.800-208) further requires key generation and signing to take place in a hardware module which does not allow the private key to be exported, which a key pair whose input values are derived from a master secret does not satisfy.

For XMSS<sup>MT</sup>, SP 800-208 requires a separate S_XMSS and SK_PRF for every XMSS key pair in the instance, because it assumes the trees to be generated in different cryptographic modules. This specification uses one S_XMSS and one SK_PRF for the whole instance, as the XMSS<sup>MT</sup> private key of RFC 8391 does, with the layer and tree fields of ADRS separating the trees. SLH-DSA uses the same construction for its hypertree.

### 10. Composite schemes

Key pairs of a hybrid scheme whose specification defines a key generation function should be generated in accordance with that specification, not composed from key pairs of the schemes it combines. For example, the private key of X-Wing is a single 32-byte seed, which its key generation expands into the input values of ML-KEM-768 and the secret key of X25519. A key pair composed from separately derived parts would have no corresponding seed. It could therefore not be exported in the standard format of X-Wing private keys, nor used with implementations whose interface accepts the seed but not the individual keys.

A composite signature or an HSS hierarchy defines no key generation beyond that of its parts, which are already in the registry. Which key pairs it combines, and at which paths they are derived, is a decision of the application. For example, the classical half of a hybrid account may be an existing key pair derived under BIP 32. A row for the composition would fix choices which belong to the application, and for HSS, whose levels may differ in their parameters, it could not list them all. This is why the registry lists LMS but not HSS.

### 11. Encoding of integer labels

The decimal ASCII encoding is chosen for three reasons:

(a) The bytes which enter HMAC-SHA512 are the bytes a human reads in the path. The decimal representation of an integer is so standard that there is no width or endianness to agree on, and test vectors can be inspected directly.

(b) It is canonical, since leading zeros are not permitted, so two implementations independently encoding the same integer always produce the same bytes.

(c) Programming environments support integer-to-decimal conversion, usually natively and with no library dependency.

Fixed-width binary encodings (e.g., 4-byte big-endian) were rejected because they impose an artificial range limit and invite confusion with the hardened bit of BIP 32 indices. Their compactness is of little value, since a label is only an input to HMAC-SHA512, and a path which is transmitted or stored can represent its integers in any form. Minimal-length binary encodings are as cheap and as canonical as decimal, but they require implementations to agree on details such as endianness, where mistakes are easy to make.

The encoding is mandatory rather than recommended because a label is a byte string which does not record whether it was meant as an integer, so canonicality can only be ensured by every implementation following the same rule. An implementation which receives labels as byte strings cannot tell whether `"0397"` was meant as the integer 397, and the two labels derive different nodes. This is not a security problem, since every byte string is a valid SLIP 21 label, but it is an interoperability hazard. Device protocols should therefore transmit integer labels as integers and encode them on the device, so that canonicality is enforced by construction.
