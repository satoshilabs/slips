## Abstract

This document defines how the inputs to the key generation of cryptographic schemes are derived from [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) nodes, together with a registry of currently supported schemes.

## Motivation

The standardization of post-quantum cryptography has created a need to derive the inputs to the key generation of schemes such as ML-DSA ([FIPS 204](https://doi.org/10.6028/NIST.FIPS.204)) and SLH-DSA ([FIPS 205](https://doi.org/10.6028/NIST.FIPS.205)) deterministically from a single master secret, so that a wallet can be restored from its backup.

[BIP 32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki) and [SLIP 10](https://github.com/satoshilabs/slips/blob/master/slip-0010.md) derive a hierarchy of key pairs in a way that supports public derivation: for the elliptic-curve schemes they cover, child public keys can be derived from parent public keys without access to the corresponding private keys. This is possible because of the homomorphism between scalar addition and point addition that elliptic-curve schemes provide. Schemes without such structure, including all current post-quantum signature standards, do not admit public derivation. For these schemes it is more straightforward to derive the inputs to the key generation as [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) secret keys, which applies uniformly to any scheme whose key generation takes inputs of fixed length.<sup>[1](#Slip10)</sup>

## Derivation of keygen inputs

For a [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) node *N*, Key(*N*) denotes its 32-byte secret key and ChildNode(*N*, *label*) denotes its child node with the given label, both as defined in SLIP 21.

A *scheme* is a cryptographic scheme with a specific parameter set, as listed in the registry below. The *scheme label* is the label which identifies the scheme. A *key pair* is the output of the key generation of a scheme and a *keygen input* is an input to that key generation.

Keygen inputs are derived at paths of the form:

```
m / <application labels> / <scheme label> / <application labels> / <input labels>
```

where the application labels are defined by the specification of the application in accordance with SLIP 21 and the *input labels* are the sequence of labels assigned to the keygen input in the registry. Every keygen input currently in the registry is assigned a single input label. The following rules apply.

1. The scheme label MUST be a level of its own, i.e., it MUST NOT encode any other parameter.<sup>[3](#SchemePosition)</sup>
2. A path MUST contain exactly one scheme label. The specification of the application MUST determine the level of the scheme label from the labels which precede it.<sup>[4](#Uniqueness)</sup>
3. An application label SHOULD NOT coincide with a scheme label listed in the registry.<sup>[3](#SchemePosition)</sup>
4. Integer labels MUST be encoded in accordance with the section "Encoding of integer labels".
5. An application which distinguishes several uses of key pairs of the same scheme, for example several output script types, SHOULD place the distinguishing label below the account, as in [SLIP 25](https://github.com/satoshilabs/slips/blob/master/slip-0025.md).<sup>[5](#ApplicationLabels)</sup>

The *key pair node* is the node at the path `m / <application labels> / <scheme label> / <application labels>`. Let *N* be the key pair node. The keygen input with the single input label *label* is<sup>[6](#ChildNodes)</sup>

```
Key(ChildNode(N, label))[0:length]
```

where *label*<sup>[7](#InputLabels)</sup> and *length*<sup>[8](#LongerInputs)</sup> are taken from the registry row of the scheme. The node ChildNode(*N*, *label*) is called an *input node*. The Usage column of the registry specifies how the keygen inputs are interpreted by the scheme.

A scheme label containing braces stands for one row for each choice of the alternatives in the braces. Each such choice is a distinct scheme and is written out in full in the path.<sup>[9](#SchemeLabels)</sup> Where the Length column lists several values, they apply to the input labels in order.

The Security strength column gives the security strength in bits which the standard of the scheme requires of the random bit generator used in key generation. See the section "Entropy of the master secret".

The keygen inputs of a scheme are the values which the standard of the scheme requires to be generated by a random bit generator for the key generation algorithm identified in the Usage column, whether the algorithm takes them as arguments or generates them itself, including values which become part of the public key. Their input labels are the names used in that standard, copied verbatim, except that a name which is not ASCII is replaced by the name the standard uses for it, as in `"seed"` for *ξ*.<sup>[7](#InputLabels)</sup>

The LMS scheme label combines the LMS parameter set with the Winternitz parameter *w* of the LM-OTS parameter set, since [SP 800-208](https://doi.org/10.6028/NIST.SP.800-208) requires the two to use the same hash function and output length. For example, `LMS_SHA256_M32_H10_W4` denotes `LMS_SHA256_M32_H10` with `LMOTS_SHA256_N32_W4`.

XMSS, XMSS<sup>MT</sup> and LMS are stateful. An application using a stateful scheme MUST ensure that no one-time key signs more than one message, including after restoration from backup. How the application does so is outside the scope of this specification.<sup>[10](#Stateful)</sup>

Future schemes are added by extending this table.<sup>[11](#Composite)</sup> The input labels of a scheme MUST be suffix-free, i.e., the sequence of labels assigned to one keygen input MUST NOT end in the sequence assigned to another keygen input of the same scheme.<sup>[4](#Uniqueness)</sup>

### Example paths

The key pair node of an account on an account-based chain, here [SLIP 44](https://github.com/satoshilabs/slips/blob/master/slip-0044.md) coin type 60 (Ether), account index 2, where SLIP 9999 stands for the specification of the application:

```
m / "SLIP-9999" / "60" / "2" / "ML-DSA-44"
```

The seed *ξ* is the secret key of the child node of this node with label `"seed"`.

The key pair node of an address on a UTXO-based chain, here coin type 0 (Bitcoin), account index 2, internal chain (change) 1, address index 14:

```
m / "SLIP-9999" / "0" / "2" / "SLH-DSA-SHAKE-128s" / "1" / "14"
```

The three keygen inputs are the secret keys of the child nodes of this node with labels `"SK.seed"`, `"SK.prf"` and `"PK.seed"`.

The application labels are illustrative. Their structure is defined by the specification of the application.

## Encoding of integer labels

When an integer is used as a path label, it MUST be encoded as its shortest possible decimal ASCII representation.<sup>[12](#IntegerLabels)</sup> Specifically:

* The integer MUST be non-negative.
* The encoding consists of the ASCII digits 0 to 9 only.
* No leading zeros are permitted, except that the integer 0 is encoded as `"0"` (the single byte 0x30).

This encoding matches the convention of [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md). Applications requiring signed or otherwise structured indices may define their own encoding, provided it is documented in the application's specification and does not produce labels consisting of ASCII digits only.

## Entropy of the master secret

The security strength of a key pair whose keygen inputs are derived under this specification is at most the entropy of the master secret. An application MUST NOT target a security strength which exceeds that entropy. A scheme whose security strength exceeds the target may still be used to retain a margin against advances in the cryptanalysis of the scheme.<sup>[13](#Entropy)</sup>

## Design rationale

### <a name="Slip10"></a>1. Extension of SLIP 21 rather than SLIP 10

The alternative we considered was to add each post-quantum scheme to [SLIP 10](https://github.com/satoshilabs/slips/blob/master/slip-0010.md) in the way ed25519 was added, with a new master key string and hardened derivation only. We rejected it for the following reasons.

1. The chain code of SLIP 10 has no remaining purpose. In [BIP 32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki) the chain code exists so that child public keys can be derived from a parent public key without revealing the parent private key. For a scheme that does not admit public derivation there is nothing for it to do. What remains of the BIP 32 structure, the chain code, the zero byte padding the private key to 33 bytes and the retry step in master key generation, is carried along without serving any function.

2. In SLIP 10 the private key of a node is both the key used by the application and the only secret which enters the derivation of its children. The chain code enters the derivation as well, but it is serialized alongside the public key and is routinely exported. Thus, if the private key of a node leaks, so does the entire subtree beneath it. In [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) the first half of a node is used only to derive children and the second half is used only as the secret key of that node. A leaked secret key never compromises the child nodes of its node.

3. In SLIP 10 the secret enters HMAC-SHA512 as the message. See item [2](#HmacArguments).

4. The output is a single 32-byte value. SLIP 10 produces exactly one 32-byte private key per node. ML-DSA takes a 32-byte seed and fits. SLH-DSA takes three values and ML-KEM takes two, and neither fits without a further rule for splitting or expanding the output, which SLIP 10 does not provide.

None of these is a weakness that an attacker can exploit. When ed25519 was added to SLIP 10, a construction with public derivation was available [KL17] and was foregone. For ML-DSA and SLH-DSA no such construction exists, so the choice is between two hardened-only trees and the question is only which structure fits the schemes.

### <a name="HmacArguments"></a>2. Roles of the HMAC arguments

HMAC-SHA512 is used in SLIP 21 in two roles. In the derivation of the master node, the master secret *S* is the message and a public constant is the key. *S* may be of any length and is not assumed to be uniformly random, so it cannot serve as a PRF key. In this role HMAC acts as a randomness extractor, as in the extract step of HKDF ([RFC 5869](https://www.rfc-editor.org/rfc/rfc5869)).

In the derivation of every child node, including every node of this specification, the secret is the HMAC key and the message is a public label. In this role HMAC is a pseudorandom function in the conventional sense, which holds for keys of any sufficient length under assumptions on the compression function alone [BBGS23].

Hardened child derivation in BIP 32 and SLIP 10 places a secret which is already pseudorandom in the message argument with the chain code as the key. For an adversary who holds the chain code this relies on HMAC being a PRF when keyed through its message argument. This property is not implied by conventional PRF security. It holds only when the values in the key argument are restricted to suitable sets, and its proof requires collision resistance of the compression function in addition [BBGS23].

Furthermore, HMAC processes its key in a block of its own, so that the key never shares an input block of the compression function with data chosen by the attacker. When the secret is placed in the message, this isolation is spent on the chain code and the secret shares a block with the index, which is no better than a plain hash of the concatenation. In BIP 32 the ordering follows from using one function for both hardened and non-hardened derivation, where in the latter the chain code is the only secret. A scheme without non-hardened derivation gains nothing from it.

### <a name="SchemePosition"></a>3. Position of the scheme label

The position of the scheme label is left to the specification of the application. A node determines all nodes beneath it, so the position decides which sets of key pairs can be provided to another party as a single node. For example, an application which places the scheme label below the coin type can provide all key pairs of one coin across all schemes, or those of one scheme only.

We considered fixing the scheme label at the first level, in the manner of SLIP 10, where each curve has a tree of its own. This would have prevented an application from providing all of its key pairs as a single node.

The scheme label is required to be a level of its own even in an application which uses a single scheme, where SLIP 21 would recommend combining it with a neighbouring fixed parameter. This keeps the scheme recognizable in every path. For the same reason a scheme label is discouraged at any other level. This is a recommendation only, since the registry may later add a label which an application already uses.

### <a name="Uniqueness"></a>4. Uniqueness of keygen inputs

A path can be read in only one way, since it contains exactly one scheme label at a level determined by the labels which precede it. Otherwise the same node could be the key pair node of two schemes and the same keygen inputs would generate a key pair under each. Thus two paths which coincide have the same scheme.

Were the input labels of one keygen input to end in those of another, the labels preceding the input labels in one path could absorb the rest of the other and two keygen inputs would coincide. This is why the input labels of a scheme are required to be suffix-free.

If the path of one key pair node happens to end in the input labels of another key pair, the node at that path serves both as an input node and as a parent node. The two roles use the two halves of the node, the first for the derivation of child nodes and the second as the secret key, so there is no conflict.

### <a name="ApplicationLabels"></a>5. Application labels

The application labels are left to the specification of the application. This avoids prematurely committing to a particular structure (e.g., BIP 32-style account indices, named identities, or random tags) and allows future SLIPs to define application-specific path layouts on top of SLIP 27.

For UTXO-based chains we recommend the shape of [SLIP 25](https://github.com/satoshilabs/slips/blob/master/slip-0025.md), which follows [BIP 48](https://github.com/bitcoin/bips/blob/master/bip-0048.mediawiki) in placing the script type below the account. BIPs [44](https://github.com/bitcoin/bips/blob/master/bip-0044.mediawiki), [49](https://github.com/bitcoin/bips/blob/master/bip-0049.mediawiki), [84](https://github.com/bitcoin/bips/blob/master/bip-0084.mediawiki) and [86](https://github.com/bitcoin/bips/blob/master/bip-0086.mediawiki) place the field that distinguishes the script type above the coin type and the account, which ties an account to a single script type. An account which spans all script types is what the user perceives as one account, which is why this specification recommends the placement of SLIP 25.

### <a name="ChildNodes"></a>6. Keygen inputs as child nodes

Each keygen input is the secret key of its own SLIP 21 node rather than a slice of a single expanded output. We considered defining a function which expands the secret key of a node to an arbitrary length, in the manner of the counter mode of [NIST SP 800-108](https://doi.org/10.6028/NIST.SP.800-108r1-upd1), and taking the keygen inputs from consecutive bytes of its output. The two constructions are equivalent under the assumption that HMAC-SHA512 is a pseudorandom function, but the child node construction introduces no new operation on SLIP 21 nodes, so that every keygen input is the secret key of a SLIP 21 node, and it requires no table of byte offsets, since the name of the keygen input is its label.

We also considered deriving the keygen inputs by feeding the secret key of the node into the extendable-output function of the scheme itself, for example SHAKE256 in the case of SLH-DSA. This would require a second primitive and a separate expansion rule for every scheme. This is why keygen inputs are derived as child nodes.

### <a name="InputLabels"></a>7. Input labels

The keygen inputs of a scheme are determined by a single criterion, so that adding a scheme to the registry involves no choice. Values which become part of the public key, such as PK.seed of SLH-DSA, SEED of XMSS and I of LMS, are included because the key pair cannot be restored from backup without them. The input labels are copied from the standard, so that a registry row reads as the interface of the key generation algorithm it refers to.

### <a name="LongerInputs"></a>8. Longer and range-restricted keygen inputs

Every keygen input in the registry is at most 32 bytes long and every value of it is accepted by the scheme, so the secret key of the input node suffices. This specification deliberately does not define how to derive a keygen input longer than 32 bytes or one which the scheme may reject, since no supported scheme requires either.

If a future scheme does, we envisage taking the keygen input from the secret keys of the child nodes of the input node with labels `"0"`, `"1"`, `"2"` and so on, concatenated and truncated to the required length, with a rejected value replaced by the next such chunk. The counter would be a second input label, which is why the input labels of a keygen input are defined as a sequence. This remains within SLIP 21 and requires no change to the existing rows of the registry.

### <a name="SchemeLabels"></a>9. Scheme labels

Each scheme label is the canonical FIPS or RFC spelling of the scheme, including the parameter set (e.g., `ML-DSA-44` rather than `ML-DSA`). Different parameter sets of the same scheme family are different cryptographic schemes, and a row with braces lists several of them only where every other column is identical. This ensures that two applications referencing the same path produce interoperable secrets without implicit assumptions about parameter selection.

Keygen inputs must never be shared between two parameter sets of a hash-based scheme in particular, since the one-time keys are derived from them by address and two tree shapes can collide on an address.

### <a name="Stateful"></a>10. Stateful schemes

XMSS, XMSS<sup>MT</sup> and LMS take keygen inputs of the same kind as SLH-DSA, which are derived in the same way. Their security depends on never signing twice with the same one-time key, and the state which prevents this cannot be derived from the master secret. A wallet restored from its backup holds the key pair without the state. Managing the state is left to the application.

[SP 800-208](https://doi.org/10.6028/NIST.SP.800-208) further requires key generation and signing to take place in a hardware module which does not allow the private key to be exported, which a key pair whose keygen inputs are derived from a master secret does not satisfy.

For XMSS<sup>MT</sup>, SP 800-208 requires a separate S_XMSS and SK_PRF for every XMSS key pair in the instance, because it assumes the trees to be generated in different cryptographic modules. This specification uses one S_XMSS and one SK_PRF for the whole instance, as the XMSS<sup>MT</sup> private key of RFC 8391 does, with the layer and tree fields of ADRS separating the trees. SLH-DSA uses the same construction for its hypertree.

### <a name="Composite"></a>11. Composite schemes

A hybrid scheme with a key generation of its own, such as X-Wing, is a scheme in the sense of this specification. A construction which combines independently generated key pairs, such as a composite signature or an HSS hierarchy of LMS key pairs, is composed by the application from key pairs at paths of its choosing and needs no row in the registry. This is why the registry lists LMS but not HSS.

### <a name="IntegerLabels"></a>12. Encoding of integer labels

The decimal ASCII encoding is chosen for three reasons:

1. It has no implementation cost. Every programming environment supports integer-to-decimal conversion natively, with no library dependency.
2. It is canonical when restricted as specified (no leading zeros, non-negative), so two implementations independently encoding the same integer always produce the same bytes.
3. The bytes which enter HMAC-SHA512 are the bytes a human reads in the path. There is no separate serialization layer, so there is no width, endianness, sign convention or hardened flag to agree on, and test vectors can be inspected directly.

Fixed-width binary encodings (e.g., 4-byte big-endian) were rejected because they impose an artificial range limit and invite confusion with the hardened bit of BIP 32 indices, without offering any compensating advantage in this context, where the encoded bytes are consumed by HMAC rather than transmitted on the wire. Minimal-length binary encodings are as cheap and as canonical as decimal, but they reintroduce the serialization layer, where mistakes are easy to make.

The encoding is mandatory rather than recommended because canonicality is a convention rather than a type. An implementation which receives labels as byte strings cannot tell whether `"0397"` was meant as the integer 397, and the two labels derive different nodes. This is not a security problem, since every byte string is a valid SLIP 21 label, but it is an interoperability hazard. Device protocols should therefore transmit integer labels as integers and encode them on the device, so that canonicality is enforced by construction.

### <a name="Entropy"></a>13. Entropy of the master secret

[FIPS 203](https://doi.org/10.6028/NIST.FIPS.203), [FIPS 204](https://doi.org/10.6028/NIST.FIPS.204), [FIPS 205](https://doi.org/10.6028/NIST.FIPS.205) and SP 800-208 require the random bit generator used in key generation to have at least the security strength of the parameter set. The analogue in this specification is the entropy of the source of the master secret, typically a mnemonic, which the derivation cannot verify.

A requirement that the entropy match the security strength of the scheme would forbid choosing a scheme above the target security strength for the sake of a margin, in the way [X-Wing](https://eprint.iacr.org/2024/039) combines ML-KEM-768 with X25519 for a security strength of 128 bits. The requirement is therefore placed on the target security strength rather than on the scheme.

A 12-word [BIP 39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki) mnemonic or a 20-word [SLIP 39](https://github.com/satoshilabs/slips/blob/master/slip-0039.md) share has 128 bits of entropy and supports any scheme in the registry at a target security strength of 128 bits, and no scheme at a higher target. A passphrase cannot be counted, since its entropy is unknown.
