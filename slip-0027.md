## Abstract

This document defines a path structure under which the secret inputs to the key generation of cryptographic schemes are derived from [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) nodes, together with a registry of currently supported schemes.

## Motivation

The standardization of post-quantum cryptography has created a need to derive the secret inputs to the key generation of schemes such as ML-DSA ([FIPS 204](https://doi.org/10.6028/NIST.FIPS.204)) and SLH-DSA ([FIPS 205](https://doi.org/10.6028/NIST.FIPS.205)) deterministically from a single master secret, so that a wallet can be restored from its backup.

[BIP 32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki) and [SLIP 10](https://github.com/satoshilabs/slips/blob/master/slip-0010.md) derive a hierarchy of key pairs in a way that supports public derivation: for the elliptic-curve schemes they cover, child public keys can be derived from parent public keys without access to the corresponding private keys. This is possible because of the homomorphism between scalar addition and point addition that elliptic-curve schemes provide. Schemes without such structure, including all current post-quantum signature standards, do not admit public derivation. For these schemes, the [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) approach of deriving a secret seed and then invoking the scheme's standard key generation function is more straightforward and applies uniformly to any scheme that accepts a fixed-length seed.

## Cryptographic scheme secret derivation

For a [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) node *N*, i.e., a 64-byte string, Key(*N*) = *N*[32:64] denotes its 32-byte key and ChildNode(*N*, *label*) denotes its child with label *label*, both as defined in SLIP 21.

Secrets for cryptographic schemes are derived under the path:

```
m / "SLIP-0027" / scheme / <application-defined>
```

where *scheme* is the canonical name of the scheme and parameter set as listed in the registry below. The labels following *scheme* are application-defined. Applications using integer labels MUST encode them in accordance with the section "Encoding of integer labels". Applications deriving secrets for a blockchain asset SHOULD identify the asset by its registered [SLIP 44](https://github.com/satoshilabs/slips/blob/master/slip-0044.md) coin type as the first label following *scheme*. Applications that distinguish several uses of keys of the same scheme and coin type, for example several output script types, SHOULD place the distinguishing label below the account, as in [SLIP 25](https://github.com/satoshilabs/slips/blob/master/slip-0025.md).

Let *N* be the SLIP 21 node at any path of the form above. Each secret input to the key generation of the scheme is called a *component*. Each component is taken from a *component node* *C*, which is determined as follows:

* If the scheme has a single component, then *C* = *N*.
* If the scheme has several components, then *C* = ChildNode(*N*, *label*), where *label* is the name of the component given in the registry.

The component is Key(*C*)[0:*length*], where *length* is taken from the registry row corresponding to *scheme*. The Usage column of the registry specifies how the component is interpreted by the scheme.

### Example paths

An account key on an account-based chain, here coin type 60 (Ether), account index 2:

```
m / "SLIP-0027" / "ML-DSA-44" / "60" / "2"
```

An address key on a UTXO-based chain, here coin type 0 (Bitcoin), account index 2, script type 0, internal chain (change) 1, address index 14:

```
m / "SLIP-0027" / "SLH-DSA-SHAKE-128s" / "0" / "2" / "0" / "1" / "14"
```

The three components of the SLH-DSA key are the keys of the children of this node with labels `"SK.seed"`, `"SK.prf"` and `"PK.seed"`.

The labels following the coin type are illustrative. Their structure is application-defined and may be standardized by future SLIPs.

## Encoding of integer labels

When an integer is used as a path label, it MUST be encoded as its shortest possible decimal ASCII representation. Specifically:

* The integer MUST be non-negative.
* The encoding consists of the ASCII digits 0 to 9 only.
* No leading zeros are permitted, except that the integer 0 is encoded as `"0"` (the single byte 0x30).

This encoding matches the convention of [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md). Applications requiring signed or otherwise structured indices may define their own encoding, provided it is documented in the application's specification and does not produce labels consisting of ASCII digits only.

## Design rationale

### Extension of SLIP 21 rather than SLIP 10

The alternative we considered was to add each post-quantum scheme to [SLIP 10](https://github.com/satoshilabs/slips/blob/master/slip-0010.md) in the way ed25519 was added, with a new master key string and hardened derivation only. We rejected it for the following reasons.

1. The chain code of SLIP 10 has no remaining purpose. In [BIP 32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki) the chain code exists so that child public keys can be derived from a parent public key without revealing the parent private key. For a scheme that does not admit public derivation there is nothing for it to do. What remains of the BIP 32 structure, the chain code, the zero byte padding the private key to 33 bytes and the retry step in master key generation, is carried along without serving any function.

2. In SLIP 10 the private key of a node is both the key used by the application and the only secret input to the derivation of its children. The chain code enters the derivation as well, but it is serialized alongside the public key and is routinely exported. Thus, if the private key of a node leaks, so does the entire subtree beneath it. In [SLIP 21](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) the first half of a node is used only to derive children and the second half is used only as the key of that node. A leaked key never compromises the children of its node.

3. In SLIP 10 the secret enters HMAC-SHA512 as the message. See the item on the roles of the HMAC inputs.

4. The output is a single 32-byte value. SLIP 10 produces exactly one 32-byte private key per node. ML-DSA takes a 32-byte seed and fits. SLH-DSA takes three values and ML-KEM takes two, and neither fits without a further rule for splitting or expanding the output, which SLIP 10 does not provide.

None of these is a weakness that an attacker can exploit. When ed25519 was added to SLIP 10, a construction with public derivation was available [KL17] and was foregone. For ML-DSA and SLH-DSA no such construction exists, so the choice is between two hardened-only trees and the question is only which structure fits the schemes.

### Roles of the HMAC inputs

HMAC-SHA512 is used in SLIP 21 in two roles. In the derivation of the master node, the master secret *S* is the message and a public constant is the key. *S* may be of any length and is not assumed to be uniformly random, so it cannot serve as a PRF key. In this role HMAC acts as a randomness extractor, as in the extract step of HKDF ([RFC 5869](https://www.rfc-editor.org/rfc/rfc5869)). In the derivation of every child node, including every node of this specification, the secret is the HMAC key and the message is a public label. In this role HMAC is a pseudorandom function in the conventional sense, which holds for keys of any sufficient length under assumptions on the compression function alone [BBGS23].

Hardened child derivation in BIP 32 and SLIP 10 places a secret which is already pseudorandom in the message input with the chain code as the key. For an adversary who holds the chain code this relies on HMAC being a PRF when keyed through its message input. This property is not implied by conventional PRF security. It holds only when the values in the key input are restricted to suitable sets, and its proof requires collision resistance of the compression function in addition [BBGS23]. Furthermore, HMAC processes its key in a block of its own, so that the key never shares a compression function input with data chosen by the attacker. When the secret is placed in the message, this isolation is spent on the chain code and the secret shares a block with the index, which is no better than a plain hash of the concatenation. In BIP 32 the ordering follows from using one function for both hardened and non-hardened derivation, where in the latter the chain code is the only secret. A scheme without non-hardened derivation gains nothing from it.

### Components as child nodes

Each component of a scheme is the key of its own SLIP 21 node rather than a slice of a single expanded output. We considered defining a function which expands the key of a node to an arbitrary length, in the manner of the counter mode of [NIST SP 800-108](https://doi.org/10.6028/NIST.SP.800-108r1-upd1), and taking the components from consecutive bytes of its output. The two constructions are equivalent under the assumption that HMAC-SHA512 is a pseudorandom function, but the child node construction introduces no new operation on SLIP 21 nodes and requires no table of byte offsets, since the name of the component is its label. We also considered deriving the components by feeding the key of the node into the extendable-output function of the scheme itself, for example SHAKE256 in the case of SLH-DSA. This would require a second primitive and a separate expansion rule for every scheme. This is why components are derived as child nodes.

### Direct use of the key for single-component schemes

A scheme with a single component uses the key of the node at the application path directly rather than the key of a child node with a fixed label. The child node would cost one HMAC-SHA512 computation and one level of the path without carrying any information. Note that the key of a node is its second half, whereas its children are derived from its first half. Thus a scheme which later acquires further components can derive them as children of the same node without affecting the existing component.

### Longer and range-restricted components

Every component in the registry is at most 32 bytes long and every value of it is accepted by the scheme, so the key of the component node suffices. This specification deliberately does not define how to derive a component longer than 32 bytes or a component which the scheme may reject, since no supported scheme requires either. If a future scheme does, we envisage taking the component from the keys of the children of the component node with labels `"0"`, `"1"`, `"2"` and so on, concatenated and truncated to the required length, with a rejected value replaced by the next such chunk. This remains within SLIP 21 and requires no change to the existing rows of the registry.

### Scheme naming

Each scheme is named using its canonical FIPS or RFC spelling, including the parameter set (e.g., `ML-DSA-44` rather than `ML-DSA`). Different parameter sets of the same scheme family are different cryptographic schemes at different security levels and are listed as separate rows. This ensures that two applications referencing the same path produce interoperable secrets without implicit assumptions about parameter selection.

### Component naming

Component labels are the identifiers used in the FIPS specification of the scheme, such as SK.seed. Thus a registry row reads as the interface of the key generation function it refers to. The labels contain a period and upper case letters, so they cannot be confused with the decimal integer labels of application-defined paths.

### Path structure

The path after *scheme* is left to the application. This avoids prematurely committing to a particular structure (e.g., BIP 32-style account indices, named identities, or random tags) and allows future SLIPs to define application-specific path layouts on top of SLIP 27. For UTXO-based chains we recommend the shape of [SLIP 25](https://github.com/satoshilabs/slips/blob/master/slip-0025.md), which follows [BIP 48](https://github.com/bitcoin/bips/blob/master/bip-0048.mediawiki) in placing the script type below the account. BIPs [44](https://github.com/bitcoin/bips/blob/master/bip-0044.mediawiki), [49](https://github.com/bitcoin/bips/blob/master/bip-0049.mediawiki), [84](https://github.com/bitcoin/bips/blob/master/bip-0084.mediawiki) and [86](https://github.com/bitcoin/bips/blob/master/bip-0086.mediawiki) place the field that distinguishes the script type above the coin type and the account, which ties an account to a single script type. An account which spans all script types is what the user perceives as one account.

### Encoding of integer labels

The decimal ASCII encoding is chosen for three reasons:

1. It has no implementation cost. Every programming environment supports integer-to-decimal conversion natively, with no library dependency.
2. It is canonical when restricted as specified (no leading zeros, non-negative), so two implementations independently encoding the same integer always produce the same bytes.
3. The bytes which enter HMAC-SHA512 are the bytes a human reads in the path. There is no separate serialization layer, so there is no width, endianness, sign convention or hardened flag to agree on, and test vectors can be inspected directly.

Fixed-width binary encodings (e.g., 4-byte big-endian) were rejected because they impose an artificial range limit and invite confusion with the hardened bit of BIP 32 indices, without offering any compensating advantage in this context, where the encoded bytes are consumed by HMAC rather than transmitted on the wire. Minimal-length binary encodings are as cheap and as canonical as decimal, but they reintroduce the serialization layer, where mistakes are easy to make.

The encoding is mandatory rather than recommended because canonicality is a convention rather than a type. An implementation which receives labels as byte strings cannot tell whether `"0397"` was meant as the integer 397, and the two labels derive different keys. This is not a security problem, since every byte string is a valid SLIP 21 label, but it is an interoperability hazard. Device protocols should therefore transmit integer labels as integers and encode them on the device, so that canonicality is enforced by construction.

### Backward compatibility

This specification does not modify SLIP 21 and defines no new operation on SLIP 21 nodes. Every component is the key of a SLIP 21 node. All existing SLIP 21 derivations and outputs remain bit-for-bit unchanged.
