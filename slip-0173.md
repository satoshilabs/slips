# SLIP-0173 : Registered human-readable parts for BIP-0173

```
Number:  SLIP-0173
Title:   Registered human-readable parts for BIP-0173
Type:    Standard
Status:  Active
Authors: Clark Moody <clark@clarkmoody.com>
Created: 2017-05-17
```

## Abstract

BIP-0173 defines a new format for segregated witness output addresses that contains a human-readable part that identifies the coin type.

## Motivation

The BIP repository does not want to deal with assigning the values for various coin types different than Bitcoin so we propose this SLIP to become such body.

## Registering a human-readable part

A human-readable part (HRP) is registered by opening a pull request that adds a row to one of the tables below: [Segwit addresses](#registered-human-readable-parts), [other uses of Bech32 and Bech32m](#non-segwit-compatible-uses-of-bech32--bech32m) or [codex32](#uses-of-codex32).

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT" and "MAY" in this section are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

Human-readable part:

- The HRP SHOULD consist of 2 to 6 characters, each a lower-case letter `a`-`z` or a digit. In the table of other uses of Bech32 and Bech32m, dashes are also allowed. The HRP MUST consist of 1 to 83 US-ASCII characters in the range 33-126 and it MUST NOT contain upper-case letters, as required by BIP-0173.
- The HRP SHOULD NOT contain the digit `1`, since it can be mistaken for the separator between the HRP and the data part.
- The HRP MUST NOT be equal to another registered HRP in any of the three tables, ignoring case. This includes the other HRPs in the same row, e.g. the mainnet and testnet HRP of a coin MUST be distinct.
- The HRP MUST NOT start with another registered HRP followed by `1`, e.g. `bc1x`. Otherwise the beginning of an address with this HRP would be indistinguishable from an address with HRP `bc`.
- The HRP MUST NOT match an entry with variable content, e.g. `lnbc` matches `ln[currency prefix + amount]`.
- Every row in the table of Segwit addresses MUST have a mainnet HRP.

Name:

- The name in the first column MUST NOT be empty, and it SHOULD consist of ASCII characters only. In the table of other uses of Bech32 and Bech32m, an empty name continues the project in the row above.
- The name MUST NOT be equal to another name in the same table, ignoring case. It SHOULD NOT be equal to another name in the same table after removing spaces, punctuation and parenthesized parts either, e.g. "Bit-Coin (next gen)" and "Bitcoin".
- The table of Segwit addresses MUST remain sorted alphabetically by coin name, ignoring case.

Formatting:

- Each HRP MUST be enclosed in backticks, one HRP per cell. In the table of other uses of Bech32 and Bech32m, the HRP MAY be followed by a space and `(m)` to indicate Bech32m.
- The name MUST NOT contain any whitespace characters other than single spaces.
- The row SHOULD be formatted like the other rows, with a single space after each pipe and each cell padded with spaces to the width of its column.

Commits:

- The subject of every commit that changes this document MUST start with `slip-0173:` followed by a space. If the commit also changes other files, then the subject MAY start with `multi:` instead.
- If the commit adds a row, then the subject SHOULD read `slip-0173: add <name>`, e.g. `slip-0173: add Bitcoin`.

## Uses of codex32

The codex32 format is used to store master secret data. It features an extended
checksum versus the one used in Bech32 in order to support enhanced error
correction. Codex32 uses the same notion of a human-readable part and the same
set of 32 characters as other Bech32 formats.

| Application          | Human-readable part  |
| -------------------- | -------------------- |
| CLN's HSM secret     | `cl`                 |
| BIP-0032 master seed | `ms`                 |
