# SLIP-0024 : Trezor payment request format

```
Number:  SLIP-0024
Title:   Trezor payment request format
Type:    Standard
Status:  Draft
Authors: Andrew Kozlik <andrew.kozlik@satoshilabs.com>
Created: 2021-12-09
```

## Abstract

A Trezor payment request is a message that is signed by a trusted party requesting payment of a specified amount to one or more addresses, similar in principle to [BIP-0070](https://github.com/bitcoin/bips/blob/master/bip-0070.mediawiki).
This message can be processed by a payer's wallet in such a way that the payer does not have to inspect the destination address and only needs to confirm the payment of the requested amount to the recipient that is named in the payment request.

## Motivation

Before a cryptocurrency payment can be made, the recipient of the payment needs to securely communicate their receiving address to the payer. If the communication channel between the two parties is not well secured or if one of the endpoints is compromised by malware, then an attacker may modify the address, changing it to the attacker's own address in order to receive the payment instead of the legitimate recipient. This type of attack is known as *address spoofing*.

Hardware wallets are known to be the most secure solution to cryptocurrency payments. They are generally very resilient to malware, but they do not protect the payer from address spoofing outside of the wallet. The task of authenticating the address is up to the payer who should ideally verify the correctness of the address by means of a second channel. Using multiple channels to communicate the address reduces the likelihood of an attacker being able to compromise all of them at once, but at the same time it hinders the user experience.

This specification defines a new format of payment requests which aim to make cryptocurrency payments in hardware wallets safer and more user-friendly by allowing automated authentication of merchant's addresses using digital signatures.

### Differences over BIP-0070

The Trezor payment request format is heavily inspired by the earlier [BIP-0070](https://github.com/bitcoin/bips/blob/master/bip-0070.mediawiki) specification. The main ways in which the present specification differs over BIP-0070 are summarized below.

* Adapted to the needs of hardware wallets.
  * A nonce challenge is used to guarantee freshness instead of creation/expiry time, since the current time is not reliably available in hardware wallets.
  * The way in which the payment request data is hashed is optimized for memory-constrained environments.
  * PKI is considered out of scope of this specification, thus X.509 support is not required.
* Designed for use with multiple cryptocurrencies.
* Defines new types of memo fields, which allow for new use-cases.
* The signature is required.

## Payment request items

### Recipient name

The recipient name is shown to the payer instead of the address or addresses which the payment request represents. The payer must however have the option of inspecting the addresses on the wallet's screen if they wish.

### Memos

Memos are used to provide additional information to the payer about the purpose of the payment request.
A memo may also contain information that needs to be verified by the payer or their wallet.
Until the required verification has completed successfully, such information is a claim.

A payment request may contain multiple instances of the same memo type.
For a memo type that is displayed to the payer, all instances of that memo type MUST be displayed in the same order as they are listed in the payment request.

The following types of memos are defined.

#### Text memo

A text memo is a UTF-8 encoded, plain-text note explaining the purpose of the payment request.
The note MUST be displayed to the payer in full.

#### Refund memo

A refund memo specifies the address where the payment should be refunded to the customer if necessary.
The customer's wallet MUST verify that it controls this address, see [Verifying address ownership](#verifying-address-ownership).
The wallet does not have to display this information on the screen.

#### Text details memo

A text details memo is a plain-text note containing additional details about the payment request. It consists of a title and a text body.
The note MAY be displayed to the payer either automatically, upon their request, or not displayed at all, namely if the device has limited capabilities.

#### Coin purchase memo

A coin purchase memo can be used by a cryptocurrency exchange service to inform their customer about the cryptocurrency and amount that the customer will receive in exchange for the payment they make. The customer's wallet MUST display this information on the screen. The coin purchase memo also specifies the address to which the exchange will send the cryptocurrency purchased by the customer. The customer's wallet MUST verify that it controls this address, see [Verifying address ownership](#verifying-address-ownership).

#### Statement memo

A statement memo commits to an expected result of verifying a requested output, such as the EVM calldata or Bitcoin OP_RETURN data which the output contains.
The output to which the statement applies is identified by the payload hash.

The wallet MUST verify the payload hash against the requested outputs, successfully perform the specified verification method, and verify the statement hash against the canonical verification result, see [Statement hash](#statement-hash).

The verification method defines how the transaction data is interpreted or verified and the canonical encoding of the verification result.

### Nonce

A unique challenge generated by the payer's wallet. The nonce guarantees freshness of the payment request and prevents replaying the payment request to the wallet or to another wallet. A nonce SHOULD be present whenever one or more memos are present in the payment request. A wallet MAY require a nonce to be present. A wallet MUST NOT accept a payment request containing a nonce that the wallet invalidated or did not issue. A wallet MUST invalidate a nonce when it accepts a payment request containing that nonce and MAY invalidate a nonce at any other time, for example upon expiry or when issuing a subsequent nonce. FIXME(nonce)

### Requested outputs

A list of requested outputs with amounts. The payer is requested to pay the specified amount to each of the listed outputs.

The value of *outputsHash* is computed from the outputs of the transaction being signed, so an output which does not belong to the payment request is presented to the payer as it would be if no payment request were provided.

An output is normally specified by its destination address. Some outputs, such as Bitcoin OP_RETURN outputs and EVM contract calls with calldata, cannot be fully specified by an address alone. Such outputs are specified by a *raw output specification*, whose format is defined for each coin type, see [Raw output specifications](#raw-output-specifications). The address form MUST be used if and only if the output can be fully specified by its destination address.

### Payment request signature

A digital signature of the payment request issued by a party which is trusted by the payer.

## Trusted party

The definition of a trusted party is out of scope of this specification. It is up to the wallet vendor to choose how trusted parties are defined. For example, they may be defined by one or more pinned public keys in the wallet's firmware or the trusted public keys may be user-defined. Trust can also be derived from a PKI scheme, such as X.509 in the BIP-0070 specification. However, it should be noted that X.509 is not very well suited for use in hardware wallets due to its excessive complexity, e.g. certificate extensions, expiry dates or certificate validation and revocation rules. Each trusted party may be restricted to signing payment requests only for particular recipient names. A trusted party may also be restricted to authorizing outputs with particular destinations, or to outputs which contain no calldata.

A payment request which specifies an output by its address requests payment of an amount, so the payer's exposure is bounded by the amount which they confirm. A payment request which specifies an output containing calldata authorizes a call, and the payer's exposure is not bounded by any amount in the payment request. Trusting a party to sign such a payment request is therefore trusting it with the effect of the transaction and not only with its destination.

A valid payment request signature establishes that the trusted party committed to the contents of the payment request, including any statement memos it contains.
The signature authenticates a statement memo as part of the payment request, but does not establish the result asserted by the statement as correct.
A statement is established only to the extent provided by its verification method.

## Workflows

The following describes several scenarios involving a customer paying a merchant using cryptocurrency. The customer has a hardware wallet and a wallet application running on their computer which controls the hardware wallet. The merchant has access to a signing server whose signatures are trusted by the customer's wallet.

### Basic scenario

1. The customer creates an order with the merchant and chooses to pay using Bitcoin.
2. The merchant generates a unique receiving address for the customer's order.
3. The merchant authenticates itself to the signing server and sends it the receiving address and amount to be paid.
4. The signing server returns a signed payment request to the merchant containing the merchant's name, receiving address and amount to be paid.
5. The merchant verifies that the signature matches the provided data and generates a BIP-0021 URI with the payment request signature in `slip24sig` as described [below](#usage-with-the-bip-0021-uri-scheme).
6. The customer clicks the BIP-0021 URI which opens their wallet application.
7. The wallet application creates a transaction transferring the requested amount to the merchant's address.
8. The wallet application requests a transaction signature from the hardware wallet, providing the payment request data.
9. The hardware wallet verifies that the payment request signature was issued by a trusted party and displays a confirmation dialog to the user stating the merchant's name and amount to be sent.
10. The customer confirms the dialog and the hardware wallet generates the transaction signature.
11. The wallet application broadcasts the signed transaction.
12. The merchant monitors the blockchain for a transaction transferring the requested amount to its receiving address.

If the trusted signing server is operated by a hardware wallet vendor, then in step 1 the customer may need to select the vendor of their wallet. The server may also be operated by the merchant itself, in which case the customer will have had to load the merchant's public key into their hardware wallet in advance.

### Scenario with a statement memo

When processing a payment request containing a statement memo, the wallet takes the following additional steps before relying on the statement:

1. The wallet verifies that it supports the specified verification method.
2. While processing the transaction data to be signed, the wallet computes the binary encoding of the corresponding requested output and verifies that its SHA-256 hash matches the payload hash in the statement memo.
3. The wallet obtains any additional verification data or evidence required by the verification method and performs the specified verification.
4. The wallet computes the canonical verification result as defined by the verification method and verifies that the statement hash matches that result, as specified in [Statement hash](#statement-hash).
5. Only after successful verification may the wallet rely on the result when presenting or authorizing the payment.

If the wallet does not support the verification method or if verification of a statement fails, the wallet MUST NOT authorize the transaction as satisfying the payment request.

### Scenario with a refund memo

1. The customer's wallet application selects an address which belongs to the customer and is suitable for receiving the refund of a payment.
2. The wallet application obtains two items from the hardware wallet:
    * an address authentication code for the selected refund address and
    * a nonce challenge, which the hardware wallet also records in a nonce cache in its volatile memory.
3. The wallet application provides the customer's refund address and nonce challenge to the merchant who will be receiving the payment.
4. The merchant generates a unique receiving address for the payment request.
5. The merchant authenticates itself to the signing server and sends it its receiving address, the amount to be paid, the customer's refund address and nonce challenge.
6. The signing server returns a signed payment request to the merchant.
7. The merchant verifies that the signature matches the provided data and returns the payment request to the customer's wallet application.
8. The wallet application creates a transaction transferring the requested amount to the merchant's address.
9. The wallet application requests a transaction signature from the hardware wallet, providing the payment request data together with the address authentication code of the refund address.
10. The hardware wallet takes the following steps:
    * Verifies that it issued the nonce challenge by checking its nonce cache and removes it from the cache so that the payment request cannot be reused in the future.
    * Verifies that it controls the refund address by validating the address authentication code.
    * Verifies that the payment request signature was issued by a trusted party.
    * Displays a confirmation dialog to the user stating the merchant's name and amount to be sent.
11. The customer confirms the dialog and the hardware wallet generates the transaction signature.
12. The wallet application broadcasts the signed transaction.
13. The merchant monitors the blockchain for a transaction transferring the requested amount to its receiving address.
14. If the merchant needs to refund the payment, then it may send it to the refund address that was specified in the payment request without any further interaction with the customer.

## Signature generation

The payment request signature is generated by signing the *paymentRequestDigest* using the private key of the trusted party.
The default signature scheme is ECDSA with SHA-256 and the curve secp256k1, but any other suitable signature scheme may be chosen by the trusted party instead. In case of the default scheme the signature is encoded in 64 bytes. The first 32 bytes encode the *r* component of the signature and the second 32 bytes encode the *s* component, both in big-endian byte order.

The *paymentRequestDigest* is computed by hashing the concatenation of the following fields:

* *versionMagic* (4 bytes): b"\x53\x4c\x00\x24" (this is "SL" followed by 0024 in compressed numeric form as an abbreviation for "SLIP-0024").
* *nonce* (length-prefixed binary string): an optional nonce challenge from the wallet. If a nonce is not used, then a zero-length string should be provided.
* *recipientName* (length-prefixed UTF-8 string): a human-readable string identifying the recipient of the payment.
* *n* (CompactSize integer): the number of memos which follow. The CompactSize integer MUST be encoded in the fewest possible number of bytes.
* *memo*<sub>1</sub> || *memo*<sub>2</sub> || ... || *memo*<sub>*n*</sub> (variable length): concatenation of the binary encoding of the memos, see below.
* *coinType* (4 bytes): 32-bit encoding of the SLIP-0044 coin type of the outputs in little-endian byte order.
* *outputsHash* (32 bytes): the hash of the binary encodings of all requested outputs, see below.

A text memo is encoded as the concatenation of the following fields:

* *memoType* (4 bytes): b"\x01\x00\x00\x00" (32-bit encoding of the integer 1 in little-endian byte order).
* *text* (length-prefixed UTF-8 string): a human-readable string providing information about the purpose of the payment.

A refund memo is encoded as the concatenation of the following fields:

* *memoType* (4 bytes): b"\x02\x00\x00\x00" (32-bit encoding of the integer 2 in little-endian byte order).
* *address* (length-prefixed string): the address where the payment should be refunded if necessary.

A coin purchase memo is encoded as follows:

* *memoType* (4 bytes): b"\x03\x00\x00\x00" (32-bit encoding of the integer 3 in little-endian byte order).
* *coinType* (4 bytes): 32-bit encoding of the SLIP-0044 coin type of the address where the coin purchase will be delivered in little-endian byte order.
* *amount* (length-prefixed UTF-8 string): the human-readable amount the address will receive including units, e.g. "0.025 BTC".
* *address* (length-prefixed string): the address where the coin purchase will be delivered.

A text details memo is encoded as the concatenation of the following fields:

* *memoType* (4 bytes): b"\x04\x00\x00\x00" (32-bit encoding of the integer 4 in little-endian byte order).
* *title* (length-prefixed UTF-8 string): a human-readable heading for the text.
* *text* (length-prefixed UTF-8 string): a human-readable string containing additional details about the payment.

A statement memo is encoded as the concatenation of the following fields:

* *memoType* (4 bytes): b"\x05\x00\x00\x00" (32-bit encoding of the integer 5 in little-endian byte order).
* *payloadHash* (32 bytes): SHA-256 hash identifying the requested output to which the statement applies, see [Statement hash](#statement-hash).
* *statementHash* (32 bytes): commitment to the verification result expected by the party issuing the payment request, see [Statement hash](#statement-hash).
* *verificationMethod* (4 bytes): 32-bit identifier of the verification method in little-endian byte order, see [Statement verification methods](#statement-verification-methods).
* *verificationData* (length-prefixed binary string): verification-method-specific parameters or evidence included in the payment request. A zero-length string is used if no verification data is included.

The value of *outputsHash* is computed as the hash of the concatenation of the binary encodings of the requested outputs. The binary encoding of an output is the concatenation of the following fields:

* *amount* (*coinType*-dependent length): fixed-length encoding of the amount of the requested output in little-endian byte order, expressed in the smallest unit of the given cryptocurrency (satoshis, wei, etc.). The length of the encoding is equal to the length used natively for the given *coinType* to encode amounts, e.g. 8 bytes for Bitcoin-like coins and 32 bytes for EVM assets.
* *address* (length-prefixed string): the address of the requested output, or, if the output cannot be fully specified by its destination address alone, a single 0x00 byte followed by the raw output specification of the output, see [Raw output specifications](#raw-output-specifications). FIXME(address-casing)

All variable-length fields are encoded the same way as in Bitcoin transactions, as a [length-prefixed string](https://en.bitcoin.it/wiki/Protocol_documentation#Variable_length_string), where the length is encoded as a variable-length CompactSize integer.

### Statement hash

The value of *payloadHash* is the SHA-256 hash of the binary encoding of one of the requested outputs, namely the output to which the statement applies. FIXME(section-naming)

The value of *statementHash* is computed as:

```
statementHash = SHA256(statementInfo)
```

where `statementInfo` is the concatenation of the following fields:

* *verificationMethod* (4 bytes): 32-bit encoding of the identifier of the verification method in little-endian byte order.
* *payloadHash* (32 bytes): the value of the *payloadHash* field of the statement memo.
* *verificationResult* (variable length): the canonical encoding of the verification result as defined by the verification method.

### Statement verification methods

The requested outputs to which a verification method applies, the verification procedure, the canonical encoding of the verification result, the meaning and encoding of *verificationData*, the freshness requirements of the verification result, the trust assumptions on which it depends and the requirements for presenting the verification result to the payer are defined per verification method. The verification method identifier 0 is reserved for future use and this specification assigns no meaning to it.

The canonical encoding of a verification result MUST be deterministic and MUST uniquely determine the result.

The data on which the verification result depends MUST be authenticated under a trust anchor which is defined by the verification method, or MUST be established by the wallet independently of the payment request. If the verification method specifies the party issuing the payment request as the trust anchor, then the verification result is asserted by that party.

A wallet MAY refuse to rely on a statement memo depending on the trust anchor which its verification method specifies.

A verification method MAY require evidence which is not contained in the payment request. Such evidence is not covered by the payment request signature and the verification method defines how it is authenticated and bound to *payloadHash* and to the verification result.

### Coin-specific encoding rules

In case of *coinType* 144 (XRP), if a requested output includes a destination tag, then the address field in the binary encoding of the output is appended with the string `?dt=`, followed by the destination tag formatted as a decimal integer in the fewest possible number of characters.

### Raw output specifications

A raw output specification canonically encodes the destination and any associated transaction data required to fully specify a requested output when the output cannot be fully specified by a destination address alone.

In the binary encoding of a requested output, a raw output specification is distinguished from an address by the first byte of the address field. Addresses consist of printable characters, so the first byte of an address is never in the range 0x00 to 0x1F. This specification reserves that range for alternative output encodings. The value 0x00 introduces a raw output specification. The values 0x01 to 0x1F are reserved for future use and this specification assigns no meaning to them. A wallet MUST NOT include in the computation of *outputsHash* an output encoding whose address field begins with a byte in the range 0x01 to 0x1F.

The format of the raw output specification is defined per coin type. A wallet MUST NOT include a raw output specification in the computation of *outputsHash* unless the wallet implements the corresponding definition and the specification exactly matches the corresponding destination and transaction data of the transaction being signed.

The *amount* field of an output specified by a raw output specification encodes the actual value of the output as usual.

The wallet MUST allow the payer to inspect an output specified by a raw output specification in the same way as it would present the output if no payment request were provided.

A wallet MUST NOT authorize an output with non-empty calldata as satisfying a payment request unless it presents the operation which the calldata performs and its parameters to the payer, or a statement memo applies to the output whose verification method does not specify the party issuing the payment request as the trust anchor and the wallet presents the verification result.

In case of Bitcoin-like coin types the raw output specification is the scriptPubKey of the output and is used only for outputs which have no address form. For example, an OP_RETURN output carrying the payload *d* is specified by the script `OP_RETURN <d>` and its amount is 0.

In case of EVM coin types, an output with non-empty transaction calldata is specified by a raw output specification consisting of the 20-byte destination address followed by the calldata encoded as a length-prefixed binary string. ## Usage with the BIP-0021 URI scheme

[BIP-0021](https://github.com/bitcoin/bips/blob/master/bip-0021.mediawiki) specifies a URI scheme for encoding Bitcoin payment requests. The present specification defines a new query key `slip24sig` for BIP-0021 URIs, allowing the URI to encode a basic Trezor payment request. If the `slip24sig` field is specified in the URI the `amount` and `label` fields MUST also be specified.

The value of `slip24sig` is the base64 encoding of the SLIP-0024 payment request signature. Note that any `=` characters in the base64 encoding must be percent-encoded as `%3D`. When computing the hash of the payment request the *recipientName* is taken from the`label` field of the URI. If the `message` field is specified in the URI, then the message is processed as a text memo. The *outputsHash* value is the hash of exactly one output specified by the `address` and `amount` fields of the URI. A nonce is not used and the *coinType* is 0.

## Verifying address ownership

This section is non-normative. One of the requirements in processing a refund memo or a coin purchase memo is that the customer's wallet must verify that the specified address is controlled by the wallet. The most common way of verifying address ownership by a wallet is to provide the BIP-0032 derivation path leading from the wallet's seed to the address. In cases where the address belongs to another coin type or uses non-standard parameters, address derivation can be more complicated.

In order to simplify the communication protocol with the wallet, it is more convenient to verify address ownership by means of an address authentication code. When getting an address from the hardware wallet, the wallet can return an authentication code together with the address. This authentication code is saved by the calling application and used at a later point in time to prove to a stateless hardware wallet that the address was derived from its seed.

### Address authentication code in Trezor

The address authentication code defined in this section should only be issued for addresses that are fully controlled by the wallet, i.e. only for non-multisig addresses.

Let *k* be a secret *address authentication key* derived from the wallet's master secret using the [SLIP-0021](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) method for hierarchical derivation of symmetric keys as:

```
k = Key(m/"SLIP-0024"/"Address MAC key")
```

The address authentication code is computed as:

```
mac = HMAC-SHA256(key = k, msg = addressInfo)
```

where `addressInfo` is the concatenation of the following fields:

* *coinType* (4 bytes): 32-bit encoding of the SLIP-0044 coin type of the address in little-endian byte order.
* The BIP-0032 path to derive the address from the master node, which consists of:
    * *n* (CompactSize integer): the path length.
    * *i*<sub>1</sub> || *i*<sub>2</sub> || ... || *i*<sub>*n*</sub> (variable length): concatenation of the 32-bit encodings of the child indices, each in little-endian byte order.
* *address* (length-prefixed string): the address being authenticated.

## FIXME

Each of the following points is named, and the text refers to it by that name.

* FIXME(multicall): the requirement in [Raw output specifications](#raw-output-specifications) that a payment request for an EVM coin type contains exactly one requested output is a choice. An EVM transaction has a single destination, so several requested outputs cannot be satisfied by one transaction, and several payments are therefore expressed as a single output whose calldata performs them. The alternative is to define a requested output for EVM coin types as one call of a batch which is executed by a single transaction.
    * In favour of the requirement: the list of requested outputs remains equal to the destinations of the transaction being signed, the *amount* field keeps its meaning as the value of the transaction, and no commitment to the atomicity of several payments is needed, because the calls and any guard which enforces their outcome are contained in one calldata. A statement memo applies to the whole call, so a verification result may concern the combined effect of the payments.
    * Against the requirement: the payer inspects a single call, so the individual payments are visible only if the wallet decodes its calldata, a statement memo cannot apply to an individual payment, and several payments performed by a contract call have that contract as their caller rather than the payer, unless the calls are executed by the payer's own account, see FIXME(account-execution).
    * The alternative allows a statement memo to apply to an individual payment, represents the value of each payment in the *amount* field of its output and allows the payer to inspect each payment separately. It requires the *amount* field to be defined as the value of the call rather than the value of the transaction, it requires a decision on whether the atomicity of the batch has to be committed to by the payment request, and it requires execution by a smart contract account, see FIXME(account-execution). The order of the calls is already committed to, because the binary encodings of the requested outputs are concatenated in order.
* FIXME(account-execution): the raw output specification for EVM coin types describes an ordinary transaction of an externally owned account. Execution by a smart contract account, such as a user operation or execution delegated by an externally owned account, is not described by a destination address followed by calldata, and it is the mechanism by which several payments can be performed while the caller of each of them remains the payer. A contract call which performs several payments on behalf of its caller does not have this property, because a call made by the code which that contract executes has that contract as its caller.
* FIXME(token-amount): the *amount* field of a requested output for EVM coin types is the value of the transaction, so it is zero for a payment of a token. The amount which the payer is asked to pay is then contained in the calldata and is not represented by the *amount* field.
* FIXME(address-casing): the casing of an address in the binary encoding of a requested output is not specified. EVM addresses have a mixed-case checksum form as defined in EIP-55, and the `0x` prefix is optional, so several textual forms denote the same account and two implementations may compute different values of *outputsHash* for the same output. Base58Check addresses are case-sensitive by construction and Bech32 addresses are canonically lowercase, which is why the question does not arise for Bitcoin-like coin types. Two fixes are possible:
    * Pin the encoding per coin type in [Coin-specific encoding rules](#coin-specific-encoding-rules), as is already done for the XRP destination tag, for example *In case of EVM coin types the address is encoded as lowercase hexadecimal characters prefixed with 0x.*
    * Specify that the address is encoded exactly as it appears in the payment request, in which case the wallet MUST compare the address to the destination of the output of the transaction being signed rather than to an address of its own construction.
* FIXME(nonce): a nonce is only recommended, so a payment request may be replayable to the wallet. Replaying an authorization of a call can reinstate an allowance or authorize an exchange under conditions which no longer hold, which is a greater consequence than replaying a request to pay an amount to an address. Consider requiring a nonce to be present in a payment request which contains a statement memo or an output with non-empty calldata.
* FIXME(section-naming): the [Statement hash](#statement-hash) section defines *payloadHash* as well as *statementHash*, so the *payloadHash* field refers to a section which is not named after it. Consider renaming the section or moving the definition of *payloadHash* next to the computation of *outputsHash*, whose output encoding it reuses.
* FIXME(test-vectors): there are no test vectors and no JSON schema for a statement memo. The computation of *statementHash* has a non-obvious preimage, so a test vector would be of particular value.

## Findings

The following are security findings about this specification. Each is named, and the text and the points above may refer to it by that name. A finding which has been resolved is retained and is marked as resolved.

* FINDING(action-authority), high: a payment request which specifies an output by its address requests payment of an amount, so the amount which the payer confirms bounds what the payer can lose. A payment request which specifies an output by calldata authorizes a call, and the loss is no longer bounded by any amount, because the call may grant an allowance which is spent later without any further involvement of the payer. A recipient which is entitled to have payment requests signed in its own name gains this authority without any compromise of the trusted party, unless the trusted party is restricted to outputs which contain no calldata. The requirement in [Raw output specifications](#raw-output-specifications) that the wallet presents the operation and its parameters, or an independently anchored verification result, limits this, but the payer must still understand the operation which is presented to them. Depends on FINDING(attestation-scope).
* FINDING(attester-identity), high: a statement memo is intended to shift the payer's reliance onto a party which evaluates the transaction data and attests to the result of that evaluation. No field of a statement memo identifies that party. The trust anchor is defined by the verification method, so the party is selected by the choice of verification method and by whatever indirection that method defines, and nothing requires the wallet to present the identity of the party to the payer. The payer is therefore asked to rely on a party which is not named to them, whereas the recipient of the payment is named by *recipientName*.
* FINDING(uninformative-result), medium: a verification result which does not describe the effect of the call, such as a result which asserts only that the calldata is well-formed, satisfies the requirement that the wallet presents a verification result instead of the calldata. The requirements for presenting a verification result are defined per verification method, and nothing requires a result to describe where the funds go. Depends on FINDING(attestation-scope).
* FINDING(stale-state), medium: a verification result which depends on mutable state is verified against a state anchor which the party issuing the payment request selects. The wallet has no clock and no view of the chain, so it cannot establish that the anchor is recent or canonical unless it maintains that view itself. A result which was true at an anchor of any age verifies identically to a current one. Depends on FINDING(attestation-validity).
* FINDING(method-registry), medium: the definitions of verification methods are outside the scope of this specification and no registry is named. Two definitions which are assigned the same identifier cause a payment request issued for one of them to be verified under the other, and the wallet presents a result which means something else. Because the trust anchor is defined by the verification method, the identifier also designates the party whose attestation the wallet accepts, so a collision causes the wallet to verify against the anchor of a different party. Depends on FINDING(attester-identity).
* FINDING(attestation-scope), medium: nothing relates the scope of a verification result to the exposure which the payer accepts. A verification result may be true and narrow, such as one which concerns only the destination of a transfer, while the same call also grants an allowance, and the payer relies on the result for the whole of the call. What a verification method asserts is defined by that method and is not compared with the effects which the call may have.
* FINDING(attestation-validity), medium: a statement memo carries no time at which the attestation was made and no period for which it is valid. The nonce establishes the freshness of the payment request and not of the attestation, and the wallet has no clock, so an attesting party has no means of bounding the lifetime of its claim which the wallet is able to enforce.
* FINDING(attester-accountability), medium: *statementHash* commits to the verification method, to the payload and to the verification result, and not to the party which attested to the result or to a signature of that party. Evidence which is carried in *verificationData* is covered by the payment request signature, but evidence which is supplied separately is not recorded in the payment request at all, so the payment request is not evidence of who made the claim. Reliance is shifted onto the attesting party without a record which holds that party to its claim.
* FINDING(evidence-binding), low: evidence which is not contained in the payment request is provided by the host. The verification method defines how it is authenticated and bound to *payloadHash* and to the verification result, so a method which omits part of that binding allows the host to select the evidence and thereby the result.
* FINDING(no-revocation), low: trusted parties are identified by pinned or user-defined public keys and this specification defines no expiry or revocation. A trusted party whose key is compromised authorizes calls until the key is removed from the wallet.
* FINDING(output-correspondence), resolved: the correspondence between the requested outputs and the outputs of the transaction being signed was not stated. An implementation which computed *outputsHash* from the requested outputs alone, without comparing them to the outputs of the transaction being signed, would have found that it matches the signature, presented the recipient name and signed a transaction which pays someone else. [Requested outputs](#requested-outputs) now states that *outputsHash* is computed from the outputs of the transaction being signed, and that an output which does not belong to the payment request is presented to the payer as it would be if no payment request were provided.
* FINDING(statement-bypass), resolved: a statement memo relieved the wallet of presenting the calldata regardless of the verification method of that memo. The party issuing the payment request could therefore attach a statement anchored on itself and thereby avoid presenting the calldata which it had composed. The requirement in [Raw output specifications](#raw-output-specifications) now accepts a statement memo in place of the presentation only if its verification method does not specify that party as the trust anchor.
* FINDING(opaque-presentation), resolved: the presentation of calldata was satisfied by any representation of it, including a representation which the payer cannot interpret. The requirement now names the operation which the calldata performs and its parameters.
* FINDING(action-scoping), resolved: nothing restricted which calls a trusted party may authorize. [Trusted party](#trusted-party) now states that a trusted party may also be restricted to authorizing outputs with particular destinations or to outputs which contain no calldata, and that trusting a party to sign a payment request which contains calldata is trusting it with the effect of the transaction and not only with its destination.

Dangers which are recorded as points above are FIXME(token-amount), where the amount presented to the payer is zero for a payment of a token, and FIXME(nonce), where a payment request without a nonce may be replayed to the wallet.

A mismatch of the casing of an address, an output encoding whose address field begins with a byte in the reserved range, a verification method which the wallet does not implement, a statement whose verification fails and a canonical encoding of a verification result which is not deterministic all cause the payment request to be rejected or the transaction not to be authorized, so they do not lead to a loss of funds.
