# SLIP-0024 : Trezor payment request format

```
Number:  SLIP-0024
Title:   Trezor payment request format
Type:    Standard
Status:  Draft
Authors: Andrew Kozlik <andrew.kozlik@satoshilabs.com>
Created: 2021-12-09
```

## Abstract

A Trezor payment request is a message that is signed by a trusted party requesting payment of a specified amount to one or more addresses, similar in principle to [BIP-0070](https://github.com/bitcoin/bips/blob/master/bip-0070.mediawiki).
This message can be processed by a payer's wallet in such a way that the payer does not have to inspect the destination address and only needs to confirm the payment of the requested amount to the recipient that is named in the payment request.

## Motivation

Before a cryptocurrency payment can be made, the recipient of the payment needs to securely communicate their receiving address to the payer. If the communication channel between the two parties is not well secured or if one of the endpoints is compromised by malware, then an attacker may modify the address, changing it to the attacker's own address in order to receive the payment instead of the legitimate recipient. This type of attack is known as *address spoofing*.

Hardware wallets are known to be the most secure solution to cryptocurrency payments. They are generally very resilient to malware, but they do not protect the payer from address spoofing outside of the wallet. The task of authenticating the address is up to the payer who should ideally verify the correctness of the address by means of a second channel. Using multiple channels to communicate the address reduces the likelihood of an attacker being able to compromise all of them at once, but at the same time it hinders the user experience.

This specification defines a new format of payment requests which aim to make cryptocurrency payments in hardware wallets safer and more user-friendly by allowing automated authentication of merchant's addresses using digital signatures.

### Differences over BIP-0070

The Trezor payment request format is heavily inspired by the earlier [BIP-0070](https://github.com/bitcoin/bips/blob/master/bip-0070.mediawiki) specification. The main ways in which the present specification differs over BIP-0070 are summarized below.

* Adapted to the needs of hardware wallets.
  * A nonce challenge is used to guarantee freshness instead of creation/expiry time, since the current time is not reliably available in hardware wallets.
  * The way in which the payment request data is hashed is optimized for memory-constrained environments.
  * PKI is considered out of scope of this specification, thus X.509 support is not required.
* Designed for use with multiple cryptocurrencies.
* Defines new types of memo fields, which allow for new use-cases.
* The signature is required.

## Payment request items

### Recipient name

The recipient name is shown to the payer instead of the address or addresses which the payment request represents. The payer must however have the option of inspecting the addresses on the wallet's screen if they wish.

The recipient name stands in place of the address which the payer would otherwise inspect, so the wallet MUST display it in full and MUST NOT truncate it. A wallet MUST reject a recipient name which contains a bidirectional or zero-width control character, or MUST display such a character in a form which the payer can recognize as one. Where a wallet holds a policy for the recipient names which a trusted party may sign, that policy is matched against the exact UTF-8 encoding of the name.

### Memos

Memos are used to provide additional information to the payer about the purpose of the payment request.
A memo may also contain information that needs to be verified by the payer or their wallet.
Until the required verification has completed successfully, such information is a claim.

A payment request may contain multiple instances of the same memo type.
For a memo type that is displayed to the payer, all instances of that memo type MUST be displayed in the same order as they are listed in the payment request.

The following types of memos are defined.

#### Text memo

A text memo is a UTF-8 encoded, plain-text note explaining the purpose of the payment request.
The note MUST be displayed to the payer in full.

#### Refund memo

A refund memo specifies the address where the payment should be refunded to the customer if necessary.
The customer's wallet MUST verify that it controls this address, see [Verifying address ownership](#verifying-address-ownership).
The wallet does not have to display this information on the screen.

#### Text details memo

A text details memo is a plain-text note containing additional details about the payment request. It consists of a title and a text body.
The note MAY be displayed to the payer either automatically, upon their request, or not displayed at all, namely if the device has limited capabilities.

#### Coin purchase memo

A coin purchase memo can be used by a cryptocurrency exchange service to inform their customer about the cryptocurrency and amount that the customer will receive in exchange for the payment they make. The customer's wallet MUST display this information on the screen. The coin purchase memo also specifies the address to which the exchange will send the cryptocurrency purchased by the customer. The customer's wallet MUST verify that it controls this address, see [Verifying address ownership](#verifying-address-ownership).

#### Delivery network memo

A delivery network memo identifies the network on which the coin purchase will be delivered. It applies to the coin purchase memo which precedes it, a payment request MUST NOT contain a delivery network memo which no coin purchase memo precedes, and at most one delivery network memo MAY apply to a coin purchase memo.

The customer's wallet MUST display the network together with the information of the coin purchase memo, and MUST verify that it controls the address of that coin purchase memo on that network. Where the *coinType* of a coin purchase memo does not uniquely determine the network, a delivery network memo MUST apply to it, and a wallet MUST NOT accept the coin purchase memo otherwise.

#### Statement memo

A statement memo commits to an expected result of verifying the requested outputs which it designates, such as the EVM calldata or Bitcoin OP_RETURN data which an output contains, or, where it designates none, to an expected assertion about state. It commits in addition to the context in which that result was established. Several statement memos MAY apply to the same requested output.

The wallet MUST derive the payload hash from the requested outputs which the memo designates and the verification context hash from the context which it derives itself, successfully perform the specified verification method, and verify the statement hash against those values and the canonical verification result, see [Payload hash and statement hash](#payload-hash-and-statement-hash).

#### Network memo

A network memo identifies the network on which the requested outputs are to be interpreted. A payment request applies to exactly one network and MUST NOT contain more than one network memo.

Where a payment request contains a network memo, the wallet MUST verify that its *networkId* identifies the network of the transaction being signed, and MUST NOT accept the payment request otherwise.

A network is not identified by *coinType*. A SLIP-0044 coin type identifies a coin or a derivation namespace, and the same coin type may be usable on more than one network, so a payment request which does not identify its network may be replayed from the network for which it was issued onto another one, where the same address and the same amount mean something else. Where the *coinType* of a payment request does not uniquely determine the network, the payment request MUST contain a network memo, and a wallet MUST NOT accept it otherwise. The condition is a property of the coin type and not of the wallet: a wallet which uses the coin type on one network only is exposed just as much, because the mismatch is between the network for which the payment request was issued and the network of the transaction being signed.

The encoding of *networkId* is defined for each coin type, see [Coin-specific encoding rules](#coin-specific-encoding-rules).

### Nonce

A unique challenge generated by the payer's wallet. The nonce guarantees freshness of the payment request and prevents replaying the payment request to the wallet or to another wallet. A nonce SHOULD be present whenever one or more memos are present in the payment request, and a wallet MAY require a nonce to be present in any case. A wallet MUST NOT accept a payment request which contains a statement memo or a requested output specified by a raw output specification unless it contains a nonce, and MUST NOT accept a payment request containing a nonce that the wallet invalidated or did not issue. A wallet MUST invalidate a nonce when it accepts a payment request containing that nonce. A nonce MUST NOT be predictable before the wallet issues it. Uniqueness alone does not suffice, because an attestation bound to a nonce which could be predicted does not establish that it was made afterwards.

### Requested outputs

A list of requested outputs with amounts. The payer is requested to pay the specified amount to each of the listed outputs.

The value of *outputsHash* is computed from the outputs of the transaction being signed, so an output which does not belong to the payment request is presented to the payer as it would be if no payment request were provided.

An output is normally specified by its destination address. Some outputs, such as Bitcoin OP_RETURN outputs and EVM contract calls with calldata, cannot be fully specified by an address alone. Such outputs are specified by a *raw output specification*, whose format is defined for each coin type, see [Raw output specifications](#raw-output-specifications). The address form MUST be used if and only if the destination and the transaction data belonging to the output can be fully specified by its destination address.

A raw output specification specifies the destination and transaction data of the output. It need not by itself determine the effect which the output may have on the payer's assets, so the requested output and the result which the payer expects may diverge.

The amount of an output specified by an address bounds the amount of the native asset which that output assigns to its destination. It does not by itself establish that execution at the destination, authority which the payer granted before, the inputs of the transaction or their ordering, transaction-wide fields, or another protocol which reads the transaction cannot cause further assets to leave the payer's control or confer deferred authority.

### Payment request signature

A digital signature of the payment request issued by a party which is trusted by the payer.

## Trusted party

The definition of a trusted party is out of scope of this specification. It is up to the wallet vendor to choose how trusted parties are defined. For example, they may be defined by one or more pinned public keys in the wallet's firmware or the trusted public keys may be user-defined. Trust can also be derived from a PKI scheme, such as X.509 in the BIP-0070 specification. However, it should be noted that X.509 is not very well suited for use in hardware wallets due to its excessive complexity, e.g. certificate extensions, expiry dates or certificate validation and revocation rules. Each trusted party may be restricted to signing payment requests only for particular recipient names. A trusted party may also be restricted to authorizing outputs with particular destinations, or to outputs which contain no calldata.

A payment request which specifies an output by its address authenticates a destination and an amount of the native asset. That amount is what the payer confirms, but it does not by itself bound what the transaction may cost them, because an effect may arise from execution at the destination, from authority which the payer granted before, from the context of the transaction or from another protocol which reads it. A payment request which specifies an output containing calldata authorizes a call, and the payer's exposure is not bounded by any amount in the payment request at all. Where such effects are possible, a claim about them is established only by a complete verification result, and trusting a party to sign the payment request is trusting it with the effect of the transaction and not only with its destination.

A valid payment request signature establishes that the trusted party committed to the contents of the payment request, including any statement memos it contains.
The signature authenticates a statement memo as part of the payment request, but does not establish the result asserted by the statement as correct.
A statement is established only to the extent provided by its verification method.

## Transaction effects

A payment request authenticates its requested outputs. It does not by itself authenticate every security-relevant effect of the transaction which contains them, because such an effect may depend on properties of the transaction outside the requested outputs, on the current state of the ledger or of an account, or on a protocol whose semantics are not represented by the amount and destination of an output.

A wallet MUST NOT suppress, replace or relabel a confirmation which it would otherwise require for a security-relevant property of the transaction, unless the effect of that property is fully determined by the requested output which the payment request authenticates, or is accounted for by a complete verification result whose verification context commits to that property. Otherwise the wallet MUST present the property to the payer as it would if no payment request were provided, or MUST refuse to authorize the transaction as satisfying the payment request.

A payment request does not establish the absence of semantics which belong to a protocol that neither the wallet nor an applicable verification method implements. A wallet MAY refuse to authorize a transaction whose security semantics it cannot establish as its policy requires.

## Workflows

The following describes several scenarios involving a customer paying a merchant using cryptocurrency. The customer has a hardware wallet and a wallet application running on their computer which controls the hardware wallet. The merchant has access to a signing server whose signatures are trusted by the customer's wallet.

### Basic scenario

1. The customer creates an order with the merchant and chooses to pay using Bitcoin.
2. The merchant generates a unique receiving address for the customer's order.
3. The merchant authenticates itself to the signing server and sends it the receiving address and amount to be paid.
4. The signing server returns a signed payment request to the merchant containing the merchant's name, receiving address and amount to be paid.
5. The merchant verifies that the signature matches the provided data and generates a BIP-0021 URI with the payment request signature in `slip24sig` as described [below](#usage-with-the-bip-0021-uri-scheme).
6. The customer clicks the BIP-0021 URI which opens their wallet application.
7. The wallet application creates a transaction transferring the requested amount to the merchant's address.
8. The wallet application requests a transaction signature from the hardware wallet, providing the payment request data.
9. The hardware wallet verifies that the payment request signature was issued by a trusted party and displays a confirmation dialog to the user stating the merchant's name and amount to be sent.
10. The customer confirms the dialog and the hardware wallet generates the transaction signature.
11. The wallet application broadcasts the signed transaction.
12. The merchant monitors the blockchain for a transaction transferring the requested amount to its receiving address.

If the trusted signing server is operated by a hardware wallet vendor, then in step 1 the customer may need to select the vendor of their wallet. The server may also be operated by the merchant itself, in which case the customer will have had to load the merchant's public key into their hardware wallet in advance.

### Scenario with a statement memo

When processing a payment request containing a statement memo, the wallet takes the following additional steps before relying on the statement:

1. The wallet verifies that it supports the specified verification method.
2. While processing the transaction data to be signed, the wallet derives the payload hash from the requested outputs which the statement memo designates, obtains any evidence which the verification method requires, and derives the canonical verification context.
3. The wallet performs the specified verification, computes the canonical verification result, and verifies the statement hash against those derived values, as specified in [Payload hash and statement hash](#payload-hash-and-statement-hash). Only then may it rely on the result.

If the wallet does not support the verification method or if verification of a statement fails, the wallet MUST NOT authorize the transaction as satisfying the payment request.

### Scenario with a refund memo

1. The customer's wallet application selects an address which belongs to the customer and is suitable for receiving the refund of a payment.
2. The wallet application obtains two items from the hardware wallet:
    * an address authentication code for the selected refund address and
    * a nonce challenge, which the hardware wallet also records in a nonce cache in its volatile memory.
3. The wallet application provides the customer's refund address and nonce challenge to the merchant who will be receiving the payment.
4. The merchant generates a unique receiving address for the payment request.
5. The merchant authenticates itself to the signing server and sends it its receiving address, the amount to be paid, the customer's refund address and nonce challenge.
6. The signing server returns a signed payment request to the merchant.
7. The merchant verifies that the signature matches the provided data and returns the payment request to the customer's wallet application.
8. The wallet application creates a transaction transferring the requested amount to the merchant's address.
9. The wallet application requests a transaction signature from the hardware wallet, providing the payment request data together with the address authentication code of the refund address.
10. The hardware wallet takes the following steps:
    * Verifies that it issued the nonce challenge by checking its nonce cache and removes it from the cache so that the payment request cannot be reused in the future.
    * Verifies that it controls the refund address by validating the address authentication code.
    * Verifies that the payment request signature was issued by a trusted party.
    * Displays a confirmation dialog to the user stating the merchant's name and amount to be sent.
11. The customer confirms the dialog and the hardware wallet generates the transaction signature.
12. The wallet application broadcasts the signed transaction.
13. The merchant monitors the blockchain for a transaction transferring the requested amount to its receiving address.
14. If the merchant needs to refund the payment, then it may send it to the refund address that was specified in the payment request without any further interaction with the customer.

## Signature generation

The payment request signature is generated by signing the *paymentRequestDigest* using the private key of the trusted party.
The signature scheme is a property of the trusted party and is fixed by the wallet's configuration of that party together with its key, because the payment request identifies neither the scheme nor the key. A wallet MUST NOT take the signature scheme from the payment request, and MUST NOT attempt verification under more than one scheme for a given trusted party. This specification defines the scheme ECDSA with SHA-256 and the curve secp256k1, in which the signature is encoded in 64 bytes, the first 32 bytes encoding the *r* component of the signature and the second 32 bytes the *s* component, both in big-endian byte order. Any other suitable signature scheme may be chosen by the trusted party instead.

The *paymentRequestDigest* is computed by hashing the concatenation of the following fields:

* *versionMagic* (4 bytes): b"\x53\x4c\x00\x24" (this is "SL" followed by 0024 in compressed numeric form as an abbreviation for "SLIP-0024"). A revision of this specification which changes the fields listed here, as opposed to one which assigns a new memo type, MUST change this value, so that a wallet implementing an earlier revision refuses the payment request rather than hashing a different list of fields under the same value.
* *nonce* (length-prefixed binary string): an optional nonce challenge from the wallet. If a nonce is not used, then a zero-length string should be provided.
* *recipientName* (length-prefixed UTF-8 string): a human-readable string identifying the recipient of the payment.
* *n* (CompactSize integer): the number of memos which follow.
* *memo*<sub>1</sub> || *memo*<sub>2</sub> || ... || *memo*<sub>*n*</sub> (variable length): concatenation of the binary encoding of the memos, see below.
* *coinType* (4 bytes): 32-bit encoding of the SLIP-0044 coin type of the outputs in little-endian byte order.
* *outputsHash* (32 bytes): the hash of the binary encodings of all requested outputs, see below.

A text memo is encoded as the concatenation of the following fields:

* *memoType* (4 bytes): b"\x01\x00\x00\x00" (32-bit encoding of the integer 1 in little-endian byte order).
* *text* (length-prefixed UTF-8 string): a human-readable string providing information about the purpose of the payment.

A refund memo is encoded as the concatenation of the following fields:

* *memoType* (4 bytes): b"\x02\x00\x00\x00" (32-bit encoding of the integer 2 in little-endian byte order).
* *address* (length-prefixed string): the address where the payment should be refunded if necessary.

A coin purchase memo is encoded as follows:

* *memoType* (4 bytes): b"\x03\x00\x00\x00" (32-bit encoding of the integer 3 in little-endian byte order).
* *coinType* (4 bytes): 32-bit encoding of the SLIP-0044 coin type of the address where the coin purchase will be delivered in little-endian byte order.
* *amount* (length-prefixed UTF-8 string): the human-readable amount the address will receive including units, e.g. "0.025 BTC".
* *address* (length-prefixed string): the address where the coin purchase will be delivered.

A network memo is encoded as the concatenation of the following fields:

* *memoType* (4 bytes): b"\x06\x00\x00\x00" (32-bit encoding of the integer 6 in little-endian byte order).
* *networkId* (length-prefixed binary string): canonical identifier of the network on which the requested outputs are to be interpreted, encoded according to the rules for the *coinType* of the payment request, see [Coin-specific encoding rules](#coin-specific-encoding-rules).

A delivery network memo is encoded as the concatenation of the following fields:

* *memoType* (4 bytes): b"\x07\x00\x00\x00" (32-bit encoding of the integer 7 in little-endian byte order).
* *networkId* (length-prefixed binary string): canonical identifier of the network on which the coin purchase will be delivered, encoded according to the rules for the *coinType* of the coin purchase memo to which the delivery network memo applies.

A text details memo is encoded as the concatenation of the following fields:

* *memoType* (4 bytes): b"\x04\x00\x00\x00" (32-bit encoding of the integer 4 in little-endian byte order).
* *title* (length-prefixed UTF-8 string): a human-readable heading for the text.
* *text* (length-prefixed UTF-8 string): a human-readable string containing additional details about the payment.

A statement memo is encoded as the concatenation of the following fields:

* *memoType* (4 bytes): b"\x05\x00\x00\x00" (32-bit encoding of the integer 5 in little-endian byte order).
* *payloadOutputs* (length-prefixed binary string): the requested outputs to which the statement applies, as the concatenated SHA-256 hashes of their binary encodings, 32 bytes each. A hash MUST NOT be repeated.
* *statementHash* (32 bytes): commitment to the verification result expected by the party issuing the payment request, see [Payload hash and statement hash](#payload-hash-and-statement-hash).
* *verificationMethod* (4 bytes): 32-bit identifier of the verification method in little-endian byte order, see [Statement verification methods](#statement-verification-methods).
* *attester* (length-prefixed binary string): identifier of the party which attested to the verification result, see [Statement verification methods](#statement-verification-methods).
* *verificationData* (length-prefixed binary string): verification-method-specific parameters or evidence included in the payment request. A zero-length string is used if no verification data is included.

The value of *outputsHash* is computed as the hash of the concatenation of the binary encodings of the requested outputs. The binary encoding of an output is the concatenation of the following fields:

* *amount* (*coinType*-dependent length): fixed-length encoding of the amount of the requested output in little-endian byte order, expressed in the smallest unit of the given cryptocurrency (satoshis, wei, etc.). The length of the encoding is equal to the length used natively for the given *coinType* to encode amounts, e.g. 8 bytes for Bitcoin-like coins and 32 bytes for EVM assets.
* *address* (length-prefixed string): the address of the requested output, or, if the output cannot be fully specified by its destination address alone, a single 0x00 byte followed by the raw output specification of the output, see [Raw output specifications](#raw-output-specifications).

All variable-length fields are encoded the same way as in Bitcoin transactions, as a [length-prefixed string](https://en.bitcoin.it/wiki/Protocol_documentation#Variable_length_string), where the length is encoded as a variable-length CompactSize integer. Every CompactSize integer in this specification MUST be encoded in the fewest possible number of bytes.

### Payload hash and statement hash

The *payload* of a statement memo is the requested outputs which its *payloadOutputs* field designates, and the statement memo applies to each of them. A hash in that field designates every requested output whose binary encoding it is the hash of, so identical requested outputs are designated together. A statement memo which designates no output is a *state assertion*: it asserts what its verification method defines rather than a result of verifying requested outputs, such as the balance which the address of the inputs holds in an asset.

The value of *payloadHash* is the SHA-256 hash of the concatenation of the binary encodings of the outputs of the payload, in the order in which they appear in the list of requested outputs. The payload of a state assertion is empty, so its *payloadHash* is the hash of the empty string.

The *verification context* of a statement memo is the canonical encoding, defined by its verification method, of every fact outside the payload which can affect the verification result. Authentication material whose sole purpose is to authenticate *statementHash* is not part of it, so an attestation may be carried in *verificationData* without hashing a value into its own preimage. The encoding of a verification context begins with the four bytes b"\x53\x4c\x24\x43", which distinguish it from any other value hashed by this specification.

The value of *verificationContextHash* is computed as:

```
verificationContextHash = SHA256(verificationContext)
```

Where the verification method defines no verification context, *verificationContextHash* is the SHA-256 hash of the empty string. The wallet MUST derive the verification context itself, as the verification method defines, before it relies on the statement memo.

The value of *statementHash* is computed as:

```
statementHash = SHA256(statementInfo)
```

where `statementInfo` is the concatenation of the following fields:

* *domain* (4 bytes): b"\x53\x4c\x24\x53", which distinguishes this preimage from any other value hashed by this specification.
* *verificationMethod* (4 bytes): 32-bit encoding of the identifier of the verification method in little-endian byte order.
* *attester* (length-prefixed binary string): the value of the *attester* field of the statement memo.
* *networkId* (length-prefixed binary string): the value of the *networkId* field of the network memo of the payment request, or a zero-length string if the payment request contains no network memo.
* *payloadHash* (32 bytes): the hash of the payload of the statement memo.
* *verificationContextHash* (32 bytes): the hash of the verification context of the statement memo.
* *verificationResult* (variable length): the canonical encoding of the verification result as defined by the verification method.

### Statement verification methods

A verification method defines the requested outputs to which it applies or that it is used as a state assertion, how the verification is performed, the canonical encoding of the verification context, the canonical encoding of the verification result and how an asset is named in the bound it states, the meaning and encoding of *verificationData*, the parties whose attestations it admits and the trust anchor of each, and the requirements for presenting the result to the payer. Its identifier is assigned in [Registered identifiers](#registered-identifiers).

The canonical encoding of the verification context MUST be deterministic and MUST uniquely determine every fact outside the payload which can affect the result, except authentication material whose sole purpose is to authenticate *statementHash*. Those facts include the properties of the transaction being signed, the state on which the result depends and every item of evidence, whether the payment request carries it or it is supplied separately. A verification method MAY require evidence which is not contained in the payment request, and defines how it is authenticated and how the wallet derives the verification context from it. Where the verification context determines a fact about the transaction being signed, the wallet MUST verify that fact against that transaction and MUST NOT rely on the statement memo otherwise.

The canonical encoding of a verification result MUST be deterministic, MUST uniquely determine the result, and MUST indicate whether the result depends on data which may change and whether it is *complete*. A result is complete if it accounts for every effect which authorizing the payload in the verified context may have on the payer's assets, and if its bound and its indication of deferred authority hold in every state and under every rule set of the network in which the transaction may validly execute, unless the validity or execution of the transaction enforces the conditions on which they depend. A result which holds only in the state its attesting party observed, or only under the rules in force when the transaction was signed, is not complete.

The canonical encoding of a complete result MUST state, in a form which the verification method defines, an upper bound on the amount of each asset which authorizing the payload in the verified context may cause to leave the payer's control, or that the amount is not bounded, and MUST indicate whether the payload confers *deferred authority*, meaning authority over the payer's assets which may be exercised after the transaction without further involvement of the payer. An asset named in a bound MUST be named unambiguously on the network of the payment request, which a token symbol or another display name alone does not do. The bound MUST cover a fee which may be taken in an asset other than the native asset of the coin type, and not a fee taken in the native asset. The canonical encoding of the result of a state assertion MUST NOT indicate that the result is complete and MUST NOT state a bound.

A bound is an upper bound, which is how it can hold across states the attesting party cannot distinguish or foresee: an effect which depends on an output that the payment request does not contain is bounded by what would leave the payer's control if no such output belonged to the payer, and where no bound holds across every state, what holds is that the amount is not bounded, which a complete result may state.

Where a result depends on data which may change, the verification method MUST require the payment request to contain a nonce, the nonce to be part of the canonical verification context, the evidence to be bound to that nonce, and the attestation to assert that the data was observed after the attesting party received that nonce; that assertion MUST be part of the canonical encoding of the result. Such a result is established as of that observation and not as of the execution of the transaction, so the wallet MUST present that the result depends on such data and MAY refuse to authorize an output on that basis.

The data on which a result depends MUST be authenticated under a trust anchor which the verification method defines, or MUST be established by the wallet independently of the payment request. If the verification method specifies the party issuing the payment request as the trust anchor, then the result is asserted by that party. Where a party other than the wallet attests to a result, the verification method MUST require that attestation to authenticate *statementHash*, or a value which contains *statementHash* and is unambiguously separated from any other value which this specification hashes.

A wallet MUST resolve *attester* to a party which it trusts for the specified verification method, and MUST NOT rely on the statement memo otherwise. Where the wallet presents a result, it MUST also present the identity which it holds for the party identified by *attester*. The identity presented MUST NOT be taken from the payment request, and MUST be presented under the requirements which apply to the recipient name, see [Recipient name](#recipient-name).

A wallet MAY refuse to rely on a statement memo on the basis of the trust anchor which its verification method specifies. A wallet MAY require that the statement memos which apply to an output have distinct trust anchors, and MAY require more than one such statement memo. The pair of *verificationMethod* and *attester* locates a trust anchor rather than defining one, and two such pairs may resolve to the same key, the same issuer or the same party, so a wallet which imposes that requirement obtains independence only where it decides distinctness by the anchor it resolves them to.

### Coin-specific encoding rules

In case of EVM coin types, a payment request MUST contain a network memo, *networkId* is the 64-bit encoding of the chain ID in little-endian byte order, and the wallet MUST verify that it equals the chain ID of the transaction being signed. The address in the binary encoding of a requested output is encoded as lowercase hexadecimal characters prefixed with `0x`.

In case of *coinType* 144 (XRP), if a requested output includes a destination tag, then the address field in the binary encoding of the output is appended with the string `?dt=`, followed by the destination tag formatted as a decimal integer in the fewest possible number of characters.

### Raw output specifications

A raw output specification canonically encodes the destination and any associated transaction data required to fully specify a requested output when the output cannot be fully specified by a destination address alone.

In the binary encoding of a requested output, a raw output specification is distinguished from an address by the first byte of the address field. Addresses consist of printable characters, so the first byte of an address is never in the range 0x00 to 0x1F. This specification reserves that range for alternative output encodings. The value 0x00 introduces a raw output specification. The values 0x01 to 0x1F are reserved for future use and this specification assigns no meaning to them. A wallet MUST NOT include in the computation of *outputsHash* an output encoding whose address field begins with a byte in the range 0x01 to 0x1F.

The format of the raw output specification is defined per coin type. A wallet MUST NOT include a raw output specification in the computation of *outputsHash* unless the wallet implements the corresponding definition and the specification exactly matches the corresponding destination and transaction data of the transaction being signed.

The *amount* field of an output specified by a raw output specification encodes the actual value of the output as usual. The effect of such an output on the payer's assets is nevertheless not always bounded by its amount, because its data may be read by another protocol as an instruction over assets which the payer holds.

A wallet MAY refuse to authorize an output specified by a raw output specification to which no statement memo applies.

The wallet MUST allow the payer to inspect an output specified by a raw output specification in the same way as it would present the output if no payment request were provided.

Where this specification states for a coin type that the effect of an output on the payer's assets is not bounded by its amount, a wallet MUST NOT authorize such an output as satisfying a payment request unless a complete verification result whose payload contains that output is established in one of the following ways:

* the wallet establishes the result itself, under a verification method which it implements and from information which the wallet holds or which is authenticated under a trust anchor which the wallet defines, and presents to the payer what the output does beyond transferring its amount;
* a statement memo applies to the output and the verification method of that statement memo does not specify the party issuing the payment request as the trust anchor.

The wallet MUST present the verification result of every statement memo in the payment request.

A wallet MUST NOT authorize an output as satisfying a payment request unless it presents in full every verification result which it is required to present. A result which enumerates several payments is presented in full only if every one of them is presented.

Where the wallet presents a verification result which states a bound it MUST present that bound as an amount of a named asset, and obtain the confirmation of the payer for it, in the manner in which it presents and confirms the amount of an output specified by an address, and it MUST present the indication of deferred authority. Whatever operation the output performs, the payer is then asked to confirm a bound on what they can lose, in the terms in which they confirm a payment.

A wallet MAY refuse to authorize a payment request on the basis of a state assertion which it contains. A wallet MAY refuse to authorize an output whose verification result states that the amount of an asset is not bounded, or that the payload confers deferred authority, or whose bound exceeds a limit which the wallet holds for the payer.

Where more than one complete verification result applies to the same payload, whether the wallet established it itself or a statement memo carries it, the wallet MUST present and confirm, for each asset which any of them concerns, the greatest bound which any of them states, and MUST present that the amount of an asset is not bounded if any of them so states. The wallet MUST present that the payload confers deferred authority if any of them so states. Results which state different bounds do not contradict one another, since each is an upper bound, but a wallet MAY refuse to authorize the payload when they differ. Two results of the same verification method for the same payload whose canonical encodings are not equal do not agree, and the wallet MUST NOT authorize the payload. A wallet which cannot establish that the asset which one result names is the asset which another names cannot combine their bounds and MUST NOT authorize the payload.

In case of Bitcoin-like coin types the raw output specification is the scriptPubKey of the output and is used only for outputs which have no address form. For example, an OP_RETURN output carrying the payload *d* is specified by the script `OP_RETURN <d>` and its amount is 0.

The absence of a raw output specification in a Bitcoin-like transaction does not establish the absence of semantics carried by the inputs, by their ordering or by the relationship among the outputs. Where the wallet recognizes such semantics, the requirements of [Transaction effects](#transaction-effects) apply.

In case of EVM coin types, an output with non-empty transaction calldata is specified by a raw output specification consisting of the 20-byte destination address followed by the calldata encoded as a length-prefixed binary string. The *amount* field encodes the transaction value, which is zero for a payment of a token, so it is not the amount which the payer is asked to pay. What the payer is asked to pay is stated by the bound of the verification result; the *amount* field keeps its own role, which is to be matched against the value of the transaction being signed. An EVM output with empty calldata MUST use the destination address form.

The effect of an EVM output on the payer's assets is not bounded by its amount, whatever its calldata, unless the transaction being signed provides no gas for execution at the destination and can cause no operation elsewhere which may act on the payer's assets or confer authority over them. Where no gas is provided for execution, no operation which could affect an asset of the payer or confer authority over one can execute at the destination, whether it holds code of its own or by delegation, because every such operation costs gas, so the transaction either transfers its value without one or it fails. The wallet establishes that from the gas limit of the transaction and the cost of the transaction itself, from information which the wallet holds or which is authenticated under a trust anchor which the wallet defines; information supplied with the payment request does not establish it. A wallet which cannot account for every component of that cost has not established it, because a cost understated by any amount leaves that much gas for execution, and a wallet which does not implement the gas semantics of the network and of the transaction type it is signing has not established it either, because a network may process or charge outside the execution at the destination and a transaction type may carry processing of its own. The wallet establishes it for every rule set of the network under which the signed transaction may validly execute, and not only for the one in force when it signs. A later rule set may charge less for the transaction itself, and the gas it releases becomes available for execution.

A transaction which carries an authorization list, or whose fee is paid by a mechanism which executes code or which takes an asset of the payer, causes such processing whatever is provided at the destination. In every other case processing the transaction executes code at the destination, and that code may act on authority which the payer granted before. Whether the destination holds code, of its own or by delegation, is not the test: it may change between the wallet establishing it and the transaction being executed. A payment request for an EVM coin type MUST contain exactly one requested output.

## Registered identifiers

The definitions to which the identifiers of this specification refer are outside its scope, but the identifiers themselves are assigned here, so that an identifier denotes one definition wherever it is used. Two definitions assigned the same identifier would cause a payment request issued for one of them to be verified or presented under the other.

An identifier is assigned by an entry in the table below. An entry names the thing identified and states where its definition is published. A definition which has been assigned an identifier MUST NOT be changed in a way which alters what a wallet does under it; such a change requires a new identifier.

### Memo types

The values of *memoType* are assigned by this specification, in [Signature generation](#signature-generation). A wallet MUST NOT accept a payment request which contains a memo whose *memoType* it does not recognize, because a memo carries information which the payer is to be shown or which the wallet is to verify, and the payment request signature covers that memo whether or not the wallet recognizes it.

A memo type is therefore how this specification is extended without changing *paymentRequestDigest*. A payment request which contains no memo of a newly assigned type hashes exactly as it did before that type was assigned, and a wallet which does not implement the new type refuses the payment request rather than ignoring the memo.

### Verification methods

A verification method identifier is the value of the *verificationMethod* field of a statement memo and of *statementInfo*, see [Statement verification methods](#statement-verification-methods). The identifier also designates the parties whose attestations the wallet accepts and the trust anchor of each, because those are defined by the verification method, so two definitions sharing an identifier would cause the wallet to verify a statement against the trust anchor of a different party. Identifiers 1 to 0x7FFFFFFF are assigned in the following table.

| Identifier | Verification method | Definition |
|-----------:|---------------------|------------|
| 0 | reserved | assigned no meaning by this specification |

No verification method is assigned an identifier by this revision of this document.

### Private use

Identifiers from 0x80000000 to 0xFFFFFFFF are not assigned here and are available for use by agreement between a wallet and the parties which issue payment requests to it. Such an identifier denotes a definition only for the parties which agreed on it and denotes nothing in another wallet. For a verification method the agreement is already required in another form, because a wallet MUST resolve *attester* to a party which it trusts for the specified verification method and MUST NOT rely on the statement memo otherwise.

## Usage with the BIP-0021 URI scheme

[BIP-0021](https://github.com/bitcoin/bips/blob/master/bip-0021.mediawiki) specifies a URI scheme for encoding Bitcoin payment requests. The present specification defines a new query key `slip24sig` for BIP-0021 URIs, allowing the URI to encode a basic Trezor payment request. If the `slip24sig` field is specified in the URI the `amount` and `label` fields MUST also be specified.

The value of `slip24sig` is the base64 encoding of the SLIP-0024 payment request signature. Note that any `=` characters in the base64 encoding must be percent-encoded as `%3D`. When computing the hash of the payment request the *recipientName* is taken from the`label` field of the URI. If the `message` field is specified in the URI, then the message is processed as a text memo. The *outputsHash* value is the hash of exactly one output specified by the `address` and `amount` fields of the URI. A nonce is not used, the *coinType* is 0 and no network memo is present, so the payment request is for Bitcoin.

## Verifying address ownership

This section is non-normative. One of the requirements in processing a refund memo or a coin purchase memo is that the customer's wallet must verify that the specified address is controlled by the wallet. The most common way of verifying address ownership by a wallet is to provide the BIP-0032 derivation path leading from the wallet's seed to the address. In cases where the address belongs to another coin type or uses non-standard parameters, address derivation can be more complicated.

In order to simplify the communication protocol with the wallet, it is more convenient to verify address ownership by means of an address authentication code. When getting an address from the hardware wallet, the wallet can return an authentication code together with the address. This authentication code is saved by the calling application and used at a later point in time to prove to a stateless hardware wallet that the address was derived from its seed.

### Address authentication code in Trezor

The address authentication code defined in this section should only be issued for addresses that are fully controlled by the wallet, i.e. only for non-multisig addresses.

Let *k* be a secret *address authentication key* derived from the wallet's master secret using the [SLIP-0021](https://github.com/satoshilabs/slips/blob/master/slip-0021.md) method for hierarchical derivation of symmetric keys as:

```
k = Key(m/"SLIP-0024"/"Address MAC key")
```

The address authentication code is computed as:

```
mac = HMAC-SHA256(key = k, msg = addressInfo)
```

where `addressInfo` is the concatenation of the following fields:

* *coinType* (4 bytes): 32-bit encoding of the SLIP-0044 coin type of the address in little-endian byte order.
* The BIP-0032 path to derive the address from the master node, which consists of:
    * *n* (CompactSize integer): the path length.
    * *i*<sub>1</sub> || *i*<sub>2</sub> || ... || *i*<sub>*n*</sub> (variable length): concatenation of the 32-bit encodings of the child indices, each in little-endian byte order.
* *address* (length-prefixed string): the address being authenticated.
